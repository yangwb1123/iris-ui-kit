## 一、架构评估

### 1.1 当前架构优势

5 个方向肯定了现有架构的核心设计——它们不是指出现有体系的全盘失败，而是标记可改善的边界点。架构真正的优势来自：

| 层             | 优势                                                             | 证据                                                                    |
| -------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------- |
| **Core 抽象**  | `createStore` 作为统一的反应性基石——四个框架 bridge 它，不是相反 | 方向一和方向五以不同观点审视 `notify()`，但两者都对其订阅模型有正面假设 |
| **机器契约**   | 6 台机器共享同一实现，`stop()` 修复一处即可修复全部              | 方向四确认修复成本低，因为共享路径                                      |
| **A/B/C 分类** | 菜单/选项卡/皮肤配置作为纯数据，准确归类为 A 类——应下沉          | 方向三辨识出 CMS 重复为 A 类债务                                        |
| **插件系统**   | `PluginRegistry` 接口是加性的——插件不 monkey-patch 组件          | 方向二和五依赖此稳定性——如果插件能随意替换 Portal，诊断会复杂得多       |

这些优势共同意味着：**系统是可修复的**。没有根本性的架构断层——所有 5 个方向都是修复，而非重写。

### 1.2 架构局限（跨方向主题）

超越 5 个方向各自的范围，这里有三个跨领域局限：

**L1 — 在 notify 期间缺少「读-拷贝」快照语义**
`notify()` 遍历 `[...listeners]` 的副本，但 `state` 本身被原地修改。一个监听器若调用 `setState()`，后续监听器看到的是修改后的 `state`，而非本次通知时的 `state`。这是语义上的错误：快照作用域覆盖了 listeners 集合，但未覆盖值。方向一对 listener 内重入的处理，正是此问题的表现。

**L2 — 缺少「触发时状态捕获」抽象**
机器 `stop()` 假设取消定时器 + 设置布尔标志就已足够，但未为监听器提供过渡到终止状态的过程。核心问题：**没有为清理序列提供显式的终止状态**。监听器若未收到 `'closed'` 值，便无法执行清理。`stop()` 会错过 exit actions，本质上是因为架构将 `stop()` 视为资源释放，而非状态转换。

**L3 — CK-5 型应用层复用缺失**
方向三揭露出一个模式：纯数据（menus、tabs）和纯逻辑（auth 读写、皮肤配置）在应用层重复了 4 次。desktop-os 壳层（已有分析已覆盖）和 CMS 层的重复，标志着一个系统性缺口：**没有标准模式用于在框架特定应用之间共享非组件逻辑**。已经有一个 `@iris-ui/core` 可以承载，但当前没有 `@iris-ui/demo-shared` 或 `@iris-ui/cms-shared` 包——这是工具链层面的缺口，而非概念层面。

### 1.3 关键设计决策审查

| 决策                                  | 评估                      | 理由                                                                                                                                             |
| ------------------------------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **`createStore` 使用同步 notify**     | ✅ 正确                   | 框架 bridge（`useSyncExternalStore`/`ref`/`createSignal`/`toStore`）期望同步通知。异步会破坏 React 18 并发特性。方向一和五的修复应保留同步语义。 |
| **机器 `stop()` 为「尽力取消」语义**  | ❌ 不完整                 | `stop()` 在 unmount 后默默吞掉事件，但不帮助消费者检测已终止。方向四修复应在同一接口处完成（在 `cancelPending()` 前执行 exit actions）。         |
| **Portal 禁用靠每个组件顶部手写判断** | ❌ 不可扩展               | 24-32 处重复（6-8 组件 × 4 框架）。当前每个新浮层组件都会增加样板代码。应下沉至 core。                                                           |
| **CMS demo 直接从各框架复制**         | ❌ 短期合理，长期不可持续 | 鉴于 desktop-os 壳层也有相同问题，这是尚未确立应用层共享包机制的表现。这是工具链缺口，而非认知缺口。                                             |

## 二、扩展方向

基于 5 个方向暴露的模式，这里有 5 个高价值的架构扩展方向。它们从诊断性修复出发，走向结构性改进。

### 方向 A：反应性中间件管道

**为何需要**：方向一（同步重入）和方向五（错误隔离）都涉及 `notify()` 中的遍历问题——它们触及 store 管道的相同环节，只是从不同角度切入。中间件层可以同时解决这两个问题，并提供一种机制供未来使用。

**核心挑战**：

- 中间件在通知期间不可重新排序（当前 `batch` 在 listener 遍历之上）
- 需要在不改变 `Store<T>` 公共接口的前提下保留同步语义
- 错误隔离必须保持可覆盖（不吞掉有意冒泡的异常）

**建议架构变更**：
在 `setState` → `notify` 路径中引入可选的中间件钩子：

```
setState → transform(updater) → 设置 state → enhance(notify) → 对每个监听器调用
```

两个内置中间件：`catchErrors`（方向五）捕获单个 listener 抛出的异常，`snapshotState`（方向一）在 `listener(state)` 被求值前捕获当前 `state` 的快照，使得 listener 内重入可以访问 `__snapshot`。注意：此处不涉及具体代码——仅说明关注点分离。

**对现有系统的影响**：

- 对不使用的消费者零影响（默认无中间件 = 当前行为）
- 可沿 `IrisProvider` 的插件注册链提供
- 方向一和五的修复可在已有中间件槽中就位，不需要手写替换 notify

### 方向 B：终止状态协议

**为何需要**：方向四揭示出机器没有告之消费者「已停止」的方式。在一个拥有 20+ 控制器、6 台机器和 4 个框架适配器的系统中，「默默停止但不通知」是一个系统性风险。每当有数据获取或动画定时器就绪，都需要可靠的终止检测。

**核心挑战**：

- `stop()` 当前通过设置布尔值 + 清理定时器来工作。与其仅保留此行为，不如将其改为进入一个监听器可观察到的终止状态。
- 但引入新状态会打破 `'closed'` | `'open'` 这类联合类型——类型定义中是否需要 `'__terminated__'`？（可能不需要，可用额外布尔量 `stopped` 属性代替）
- 多台机器（浮层、hover-intent、自动关闭）共享同一 `createMachine` 函数——修复一处即可修复全部（方向四已验证此条）

**建议架构变更**：
在 `MachineState` 中添加一个 `stopped?: boolean` 标志，在 `stop()` 被调用时由适配器在 cleanup 中检查：

- `stop()` 执行当前状态的 exit actions（方向四的核心修复）
- `stop()` 将 `stopped = true` 写入 store（新增行为）
- 适配器监听 `stopped` 并在值为 `true` 时执行剩余的清理工作

**对现有系统的影响**：

- 现有监听器若检查 `state.value === 'closed'`，在 `stopped = true` 时不会被错误触发
- 适配器 cleanup 可迁移为监听 `state.value === 'closed' || state.stopped`
- 类型保持：`MachineState` 获得可选标志，所有现有消费者继续工作

### 方向 C：Portal 统一层

**为何需要**：方向二量化了缺口——24-32 处重复的 portal 禁用模式 + Vue 与 React/Solid/Svelte 之间的 prop 名称不对称。每增加一个新浮层组件，所有 4 个框架都要手写一次「if inline → return node else portal」。再增加一个框架（Angular、Lit），这个模式会继续扩散。

**核心挑战**：

- Vue 的 `<Teleport>` 原生接受 `string` 选择器。若想让 Vue 消费者能继续使用 `"#modal-root"`，统一类型签名就必须包含 `string`。
- SSR 安全：`document.querySelector` 在 SSR 中不可用。`string` 目标需要标记为「Vue SSR 中自动禁用」，而非在类型层面拒绝。
- `portalTarget={false}` 的行为在所有框架中应一致——当前是手写模式，每次实现细节各不相同。

**建议架构变更**：

- 统一 prop 名为 `portalTarget`（3 对 1，Vue 改为映射自身 `<Teleport to>` prop）
- 统一类型为 `HTMLElement | string | false`
- 在 `@iris-ui/core` 中创建一个纯函数 `normalizePortalTarget(target): HTMLElement | null`（处理 string→element 查找、SSR guard、`false`→inline）
- 添加合约场景：`renderContent({ portalTarget: false })` 不应产生 portal wrapper DOM

**对现有系统的影响**：

- 每个浮层组件从 ~15 行手写 portal 逻辑缩减为 ~3 行（导入并使用该工具函数）
- 跨框架合约不再因 portal 实现细节而存在盲区
- 24-32 处重复消除，回归到一处来源

### 方向 D：应用层共享组件（`@iris-ui/demo-core`）

**为何需要**：方向三识别出 5 个 CMS 模块 × 4 框架的重复。加上 desktop-os 壳层（8 个模块 × 4 框架），项目共有 13 个模块 × 4 = 约 52 个重复文件。这是一个**可计算的维护成本**：每个新适配器增加这些文件的乘法因子。

**核心挑战**：

- 纯逻辑（`menus.ts`、`tabs.ts`）可直接下沉到共享包——它们零框架依赖。
- 框架绑定逻辑（`auth.ts` 中的 `React.createContext` vs `reactive` vs `createContext` vs `$state`）需要一个薄桥。当前 4 份 auth 实现的核心逻辑 80% 相同，仅框架绑定层不同。
- 命名冲突：`@iris-ui/cms-shared` 与 `@iris-ui/demo-core` 之争。名为 `cms-shared` 会阻止它被其他 demo 复用；名为 `demo-core` 则暗示通用性，但当前仅有 CMS 需要它。

**建议架构变更**：

- 创建 `packages/demo-core/`（命名偏向通用性——因为 CMS 的菜单/认证模式同样是任何 demo 应用都需要的东西）
- 下沉：`Session` 类型、`readStored`/`writeStored`、`login`/`logout` 纯函数、`menus: NavNode[]`、`tabsConfig`、`skinConfig`
- 每个框架的 `auth.ts` 从 ~70 行缩减为 ~20 行，仅保留框架绑定
- `menus.ts` 缩减为 ~3 行 re-export

**对现有系统的影响**：

- 当 `demo-core` 包尚未发布时，现有目录可维持运行（无破坏性变更）
- 新框架适配器（如 `cms-angular`）直接从 `demo-core` import，而非重新复制
- desktop-os 壳层随后可复用同一模式（但需要自己的下沉——`@iris-ui/os-shared` 或纳入 `demo-core`）

### 方向 E：Store 生命周期正式化

**为何需要**：方向五（错误隔离）和方向一（重入）影响 `createStore`——整个 UI 的反应性基石。方向四则影响机器生命周期。三者共同指向一个更系统性缺口：**store 拥有隐式创建，但缺少显式销毁**。`createStore(initial)` 不返回「销毁」方法。`derived` store 的引用计数订阅解除机制很好，但 `createStore` 的 listeners 集合在没有全局清理机制的情况下只能不断增长。

**核心挑战**：

- 为 store 添加 `destroy()` 方法需要清理监听器、pending flush 状态，并可选地发出终止通知。这是一项侵入性变更——每个 store 消费者都需要知道是否应当调用 `destroy()`。
- 当前，控制器（selection、expansion、data-view 等）在其宿主组件 unmount 后不自我销毁。它们由 GC 收集——但如果 store 已被全局共享（如 toast 队列、皮肤引擎），listeners 可能会泄漏。
- 通知错误隔离（方向五）是这项变更的前提：若监听器抛异常不会使整个 store 崩溃，则 `destroy()` 可以安全地断开监听器。

**建议架构变更**：

- 向 `Store<T>` 接口添加 `destroy()`（返回类型 `void`，幂等）。实现清理 listeners、pending flush 标志以及 batch depth 计数器。
- 方向五的 `try/catch` 确保 `destroy()` 在运行每个 listener 的清理逻辑时，单个 listener 抛出的异常不会阻止其他 listener 被清理。
- 方向一的重入修复确保 `destroy()` 期间若有 listener 回调调用 `setState`，不会造成数据损坏。

**对现有系统的影响**：

- 现有代码若从不调用 `destroy()`，行为不变（GC 继续正常工作）
- 对于全局共享 store（皮肤引擎、toast 队列、插件 store），`destroy()` 变为最佳实践
- 合约测试可获得 `afterEach` 重置，替代当前对全局 store 的 `vi.unstubAllGlobals` 模式

## 三、接口设计建议

### 3.1 关键模块原则

基于 5 个方向，这些原则应指导接口设计：

**P1 — Store 接口应保持同步（不变）**
方向一和五讨论同步 notify 的问题，但**不**建议引入异步。React 的 `useSyncExternalStore`、Vue 的 `ref`、Solid 的 `createSignal` 以及 Svelte 的 `toStore` 都依赖同步语义。store 接口应继续暴露 `getState()`、`setState()`、`subscribe()`——无 Promise，无回调驱动的异步。修复应在 notify 内部进行，而非通过改变契约。

**P2 — 中间件应为可选的附加物，而非内建**
方向一（重入防护）和五（错误隔离）可能催生「在 `createStore` 中放置通用中间件 API」的冲动。但存在一个问题：中间件会改变 `notify()` 的求值语义——而在当前系统下，所有四个框架 bridge 都必须将 `notify()` 视为线性同步序列。若将错误隔离或重入防护构建为中间件，中间件注册顺序可能会出现意外效果。更简单的做法是：将这两个修复直接内联到 `notify()` 中，未来如果出现需要中间件的场景，再将其作为独立项引入。

**P3 — 机器的终止状态应作为可选位，而非 enum 值**
方向四建议若将 `__terminated__` 加入 `value` 联合类型，会破坏 TypeScript 的类型收窄（`state.value === 'closed'` 仍为真，但消费者不会意识到 `'closed'` 可能出现在 dispose 之后）。更好的选择：向 `MachineState` 添加一个 `stopped?: boolean` 标志。消费者检查 `state.value === 'closed' || state.stopped` 即可优雅处理。类型保持简洁，现有代码继续工作。

### 3.2 新抽象层

| 层                                             | 是否应当引入 | 理由                                                                                                                           |
| ---------------------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| **`@iris-ui/core/portal`（Portal 工具函数）**  | ✅ 是        | 将 24-32 处重复精简为 1 处。包含 `normalizePortalTarget`、SSR guard、inline rendering。几乎无大小成本（约 30 行）。            |
| **`@iris-ui/demo-core`（共享 demo 逻辑）**     | ✅ 是        | 方向三确认 CMS 有 ~400 行重复纯逻辑。每个新适配器在不取共享包的情况下会增加 ~100 行。构建成本低（纯 TypeScript，无框架依赖）。 |
| **`RegistryPlugin` 中的 `onNotifyError` 钩子** | ❌ 否        | 方向五的 try/catch 足够用。再加一个插件钩子会引入认知开销，却几乎无新增能力。                                                  |
| **`Store.destroy()`**                          | ⚠️ 可选      | 方向四和五间接支持它，但对 GC 场景价值有限。仅作为全局共享 store 的最佳实践引入。                                              |

### 3.3 向后兼容

所有 5 个方向都可以实现为**非破坏性变更**：

| 方向           | 破坏丨非破坏   | 机制                                                                                                                                                                                          |
| -------------- | -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 一（重入）     | ✅ 非破坏      | 添加重入防护不改变现有 listener 的行为——listeners 仍同步触发，仍可见最新 `state`。仅新增的防护影响重入。                                                                                      |
| 二（Portal）   | ⚠️ Vue prop 名 | 若将 Vue 的 `teleport` 改为 `portalTarget`，旧 `teleport` prop 需要已弃用的重定向。若保留 `teleport` 作为别名，则为非破坏。                                                                   |
| 三（CMS 共享） | ✅ 非破坏      | 提取共享包后，现有文件可通过 import 重映射继续工作。                                                                                                                                          |
| 四（机器停止） | ✅ 非破坏      | `stopped?: boolean` 是可选字段。现有 `state.value === 'closed'` 检查不受影响。                                                                                                                |
| 五（错误隔离） | ✅ 非破坏      | try/catch 不改变 listener 触发方式。若消费者依赖 `setState` 抛出以触发 React 错误边界，则存在微妙的破坏风险——但当前系统下 listener 异常从不冒泡到 `setState` 调用者，因此这里没有实际的破坏。 |

## 四、技术选型

### 4.1 新依赖要求

所有 5 个方向在 `@iris-ui/core` 的当前依赖范围内即可解决——不需要新的第三方库。方向二的 Portal 工具函数可自行处理 SSR guard（`typeof document === 'undefined'` 检测），不需要 `@floating-ui/dom`——它只处理 inline 渲染决策，不处理定位。

方向三的共享 demo 包是纯 TypeScript——零运行时依赖。它通过 `package.json` 中的 `"exports"` 映射来暴露 `./auth`、`./menus`、`./tabs`、`./skin` 等子路径。

### 4.2 自建 vs 采购

所有 5 个方向都应**自建**：

| 方向               | 为什么不是已有的库                                                                                                                                        |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 方向一（重入）     | 重入检测是 store 语义问题——没有 express 级别的重入防护库。`immer` 有 freeze 但缺少重入检测。                                                              |
| 方向二（Portal）   | `@floating-ui/dom` 处理定位，但不涉及「在哪里渲染」的决策。Portal 目标规范化是 UI 库层面的事，不是浮层层面的事。                                          |
| 方向三（共享包）   | 这是一个 monorepo 组织问题，不是 npm 依赖问题——应用之间共享纯数据不能从第三方解决。                                                                       |
| 方向四（终止状态） | XState 有 `stop()` 语义，但 Iris 的机器故意保持在状态图的 80/20 范围（无并行状态、无 actors）。引入 XState 作为依赖会使核心包体积从 ~10KB 膨胀到 ~50KB+。 |
| 方向五（错误隔离） | try/catch 是语言内建。不需要库。                                                                                                                          |

### 4.3 依赖评估标准

对于未来任何第三方评估，5 个方向建议采用以下标准：

1. **框架无关性**：可以在 `@iris-ui/core` 中使用，无 React/Vue/Solid/Svelte 导入。如果库有框架特定绑定，它必须是一个可选的附加包，而非核心依赖。
2. **SSR 安全**：不会在 SSR 期间访问 `document`/`window`。方向二的 Portal 工具函数和方向四的终止状态协议都受影响。
3. **同步优先**：不会将异步 Promise 引入 `getState()`/`setState()` 路径。方向一和五依赖同步 notify。
4. **体积 < 5KB min+gzip**：方向二和五都是 ~30 行代码。若整个依赖比手写代码还大，则应自建。

## 五、实施路线图

### 5.1 优先级总结

| 排序 | 方向                     | 优先级          | 工作量估计                                            | 依赖关系                           |
| ---- | ------------------------ | --------------- | ----------------------------------------------------- | ---------------------------------- |
| 1    | **方向五：错误隔离**     | P0 — 立即       | 2 行（`notify` 中加 try/catch）+ `derived` notify     | 无                                 |
| 2    | **方向一：重入防护**     | P1 — 下一迭代   | ~10 行：捕获 `state` 快照 + `__reentering` 标志       | 可在方向五之前或之后完成（不依赖） |
| 3    | **方向四：机器停止语义** | P1 — 下一迭代   | ~15 行：`stop()` 中 exit actions + store 写 `stopped` | 无                                 |
| 4    | **方向二：Portal 统一**  | P2 — 短期路线图 | ~30-50 行：工具函数 + 合约场景 + 跨框架 prop 迁移     | 方向一（重入）非阻塞               |
| 5    | **方向三：CMS 共享**     | P3 — 中期       | ~100 行提取 + 子路径包配置                            | 方向二（Portal）非阻塞             |

> **说明**：方向三标记为 P3 而非 P2，因为 5 个方向分析文档分配了 P2，但考虑到 desktop-os 壳层重复是同一类 debt 且更重，CMS 重复的修复排在其后。若 desktop-os 壳层先解决，CMS 同步可复用同一模式，实现更简单。

### 5.2 阶段划分

**阶段 1：「防御性修复」（当前迭代）**

- 方向五：向 `notify()` 和 `derived` 的 listener 循环添加 try/catch。**改动量**：2 个位置，每处 +1 行 try/catch。
- **验证**：确认 React 错误边界不被吞掉（参见分析和建议的折中方案——不重抛）。
- **风险**：接近零——错误隔离只保护现有行为。

**阶段 2：「一致性修复」（下一迭代）**

- 方向一：在 `notify()` 中在调用 `listener(state)` 前快照 `state`，在重入时传递快照值。
- 方向四：扩展 `stop()` 以执行 exit actions 并写入 `MachineState.stopped`。
- 方向二：在 `@iris-ui/core` 中创建 `normalizePortalTarget`。统一 React/Solid/Svelte/Vue 使用相同的工具函数。
- **风险点**：
  - 方向四：exit action 中若出现 guard，或机器在 `stop()` 前已从当前状态移走，要倍加小心。应该幂等。
  - 方向二：Vue 的 `teleport` → `portalTarget` 迁移可能需要一个过渡期。

**阶段 3：「结构性改进」（短期路线图）**

- 方向三：创建 `packages/demo-core/`，提取 CMS 数据。更新四个 CMS demo 使用它。
- 验证 CMS 合约在提取后是否继续通过。
- **风险**：若 `demo-core` 产生框架特定构建（如菜单是普通数据，但 auth 需要框架绑定），子路径映射可能需维护 `auth/react`、`auth/vue` 等入口点。第一阶段保持纯逻辑，后续再考虑框架绑定。

### 5.3 风险与缓解

| 风险                                             | 影响方向 | 缓解                                                                                                                                                               |
| ------------------------------------------------ | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **方向五 try/catch 吞掉有意冒泡的异常**          | 五       | 在 `listener(state)` 的 catch 块中，不重抛。记录日志至 `console.error`，但提供全局 `onStoreError` 钩子用于外部捕获。                                               |
| **方向一快照增加分配开销**                       | 一       | 快照是 `Object.assign({}, state)`——仅最浅层。对于大型状态（如 data-view 的 ~100 行），快照可能约为 ~2KB 分配。若可测量到性能问题，在浅比较未发生变化时跳过快照。   |
| **方向四 `stop()` 中的 exit actions 可能抛异常** | 四       | 方向五的 try/catch 已经覆盖——exit actions 中的异常不打断 `stop()` 链。但若 exit action 包含清理逻辑，该清理此时已丢失。添加文档说明：「exit actions 不应抛异常。」 |
| **Vue 消费者的 Portal 行为变更**                 | 二       | 弃用 `teleport` 为别名，在下一个大版本移除。迁移指南明确说明：`teleport=".selector"` 改为 `:portalTarget="'.selector'"`。                                          |
| **demo-core 包在发布前即腐烂**                   | 三       | 这是一个应用层包——它不影响核心库消费者。若在共享过程中腐烂，CMS demo 可降级回复制模式，无外部影响。                                                                |

## 六、未竟事项（供维护者决定）

**1 — 方向一快照到底是深拷贝还是浅拷贝？**
浅拷贝（`Object.assign({}, state)`）对于扁平状态足够，但若状态包含嵌套引用（如 `{ items: [{…}, {…}] }`），listener 内对 `state.items.push(...)` 的修改仍会污染快照。若重入防护的用例涉及深层嵌套，成本会增加。当前的权衡：从浅快照开始，不承诺深层不变性。

**2 — 是否应为 store 创建全局注册表以支持调试？**
方向五的 `console.error` 会输出单个错误，但若存储 Listener 注册历史到全局注册表，调试重入会容易得多。代价是增加一个全局单例（违反了「无全局可变状态」原则）。`@iris-ui/devtools` 包可作为替代承载此功能。

**3 — 5 个方向修复之后，是否要创建「终止状态」合约？**
方向四新增 `stopped?: boolean` 后，合约序列应包含一种「创建机器 → 停止 → 验证不会再有通知发出」的模式。这确保了适配器可以信赖机器终止后的静默。但编写此合约需要 `contracts/` 目录中有存在合约——这个目录的成熟度在不同方向上有所不同。方向四的描述本身可能就足够作为验证依据。

**4 — 方向四 exit actions 是否应将合成事件命名为 `xstate.stop`？**
当前文档页面使用 `{ type: 'xstate.stop' }` 来代表合成停止事件。但 Iris 已使用自己的约定（`xstate.init` 用于初始 entry）。`xstate.stop` 是此模式的自然延续。但有一个陷阱：若 exit action 签名接受 `(context, event)`，而 event 是合成 `{ type: 'xstate.stop' }`，action 可能会基于 `event.type` 进行守卫，从而改变行为。建议用文档说明：`stop()` 执行时不应跳过 exit actions；合成事件仅用于类型签名，不应被守卫。

---

**总结**：5 个方向共同指向一套一致的架构提升：**Store 应得到通知防护（方向一、五），Machine 应具有可观察的生命周期（方向四），Portal 应统一（方向二），应用层应共享（方向三）**。所有变更均无破坏性，总计约 50-80 行核心逻辑变更 + 约 100 行共享应用代码提取。修复收益远大于成本。
