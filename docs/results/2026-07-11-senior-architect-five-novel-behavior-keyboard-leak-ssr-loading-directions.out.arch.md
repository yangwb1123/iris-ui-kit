# 架构分析报告：Iris UI 源码断言交叉验证之后

> 基于 5 方向源码断言交叉验证结论，对 Iris UI 当前架构进行系统性评估，并提出扩展方向、接口设计建议、技术选型与实施路线图。

---

## 1. 架构评估

### 1.1 当前架构的优势

Iris UI 的架构设计在 UI 基础设施领域属于**一流水平**，以下几个设计决策构成了其核心竞争力：

| 优势                      | 说明                                                                                              | 技术杠杆                                            |
| ------------------------- | ------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| **三层分离模型（A/B/C）** | 核心逻辑（A）、附加能力（B）、纯材料（C）的清晰分层，是 4 框架对齐的制度保障                      | 任何新框架适配 ≈ 薄桥 + 渲染，逻辑零重写            |
| **Token 驱动渲染**        | `var(--iris-*)` 单一绑定点，一套 token 改变整个系统视觉                                           | 皮肤系统/主题切换/FOUC 防闪均建立在此之上           |
| **插件契约轻量**          | `registerTokens`/`registerMessages`/`registerStore` 三原语，不做 `registerComponent` 防止类型退化 | 插件包可独立发布、按需 `use`、异构工具链            |
| **Controller 模式**       | `createSelectionModel`/`createExpansion`/`createAdminShell` 等控制器将状态机下沉到 core           | 17 组件共享 selection 逻辑、19 组件共享 roving 焦点 |
| **质量门完备**            | 四道门（test/typecheck/lint/build）+ size 预算 + RSC + arch-check                                 | 防止退化，确保持续集成安全                          |

### 1.2 当前架构的局限性（基于交叉验证揭示）

交叉验证的 5 个方向揭示了 4 类架构性缺口，按严重程度排列：

#### 🔴 致命级：Behavior 合约测试盲区

```
42 个合约场景文件 × 4 框架 = 168 测试套件
覆盖 accordion/dialog/popover/table/tree...
但 0 个覆盖 sortable/movable/resizable/click-outside/hotkey/long-press
```

**架构影响**：Behaviors 是 Iris UI "正交叠加能力" 的核心卖点（见 AGENTS.md：_"Behaviors = renderless/薄定位包裹器，把 resize/拖动/快捷键/点击外部叠加到任意组件"_）。但 6 个 Behaviors 的跨框架行为一致**没有任何合约级验证**。这意味着：

- 同一 Behavior 在 React/Vue/Solid/Svelte 下可能有细节行为差异
- 没有契约约束，Behavior 的框架适配器可以悄悄偏离 core 语义
- 这是架构分层最薄弱的一环——**"薄桥"假设未经验证**

#### 🟠 高风险：Store 订阅生命周期不完整

| Controller                 | 有 destroy()             | 订阅泄漏风险                                         |
| -------------------------- | ------------------------ | ---------------------------------------------------- |
| `createSelectionModel`     | ✅ 有                    | 低                                                   |
| `createExpansion`          | ✅ 有                    | 低                                                   |
| `createResourceController` | ✅ 有（委托 ds.destroy） | 低                                                   |
| `createAdminShell`         | ❌ 无                    | **高** — 包含 selection/expansion/tabsNav 多个订阅源 |
| `createStore`              | N/A（基础 store）        | **中** — 无泄漏检测/调试基础设施                     |

**架构影响**：`createAdminShell` 是 L4 系统骨架的核心控制器，管理菜单展开、标签页导航、选中状态等。它缺失 `destroy()` 意味着：

- 在 SPA 中切换 admin 页面时，订阅不会被清理
- 如果 L4 组件（AdminLayout）被卸载再挂载，会产生**幽灵订阅**
- 这是典型的"架构债务"——在使用层面上没问题（不调用 destroy 也没坏处），但在组合场景下会产生资源泄漏

#### 🟡 中风险：语义状态缺失与快捷键协议粗糙

| 问题             | 具体表现                                                                                    | 后果                               |
| ---------------- | ------------------------------------------------------------------------------------------- | ---------------------------------- | -------------------------------------------------- |
| 数据加载语义不够 | `loading: boolean` 无法区分 "首次加载" / "刷新" / "加载更多"；`AsyncStatus` 无 `refreshing` | 加载态 UI 无法差异化，用户体验折衷 |
| 快捷键冲突协调   | `scope: 'document'                                                                          | 'window'` 无优先级/协调机制        | 多个 Hotkey 实例同时监听同一组合键时，行为非确定性 |

这两个问题不致命，但代表了**设计深度不足**——架构的抽象层定义了接口，但接口的表达力不够支撑真实场景的复杂需求。

#### 🟢 低风险（但诚信受损）：Plugin Store SSR 安全

方向④的核心论点（`registerStore` 工厂急切执行可能引发 SSR 问题）本身合理。但证据伪造严重损害了文档可信度。实际只有 `plugin-editor` 使用了 `registerStore`，其余 11 个插件使用的 `registerTokens`/`registerMessages` 是声明式的，**不存在 SSR 安全风险**。

**架构启示**：需要引入**证据复核机制**——所有架构分析文档的源码断言应当标注执行时间、commit hash，并由第二人复核。

### 1.3 关键设计决策合理性回顾

| 决策                                       | 合理性评估          | 备注                                      |
| ------------------------------------------ | ------------------- | ----------------------------------------- |
| 逻辑下沉 core，适配器做薄桥                | ✅ **正确**         | 4 框架 149 组件对齐验证了此决策           |
| Token 驱动渲染，禁止硬编码/CSS-in-JS       | ✅ **正确**         | 皮肤系统、主题切换、RTL 均因此成为可能    |
| 插件不做 registerComponent                 | ✅ **正确**         | 保护了类型安全和 tree-shaking             |
| Behaviors 作为正交包裹器                   | ⚠️ **正确但需强化** | 桥的"合约验证"缺失，需要补充测试体系      |
| 状态机的克制使用                           | ✅ **正确**         | AGENTS.md 已明确判别准则，防止"svjs 退化" |
| `scope: 'document'\|'window'` 作为冲突协议 | ❌ **过于简单**     | 需引入优先级/仲裁/可组合协议              |

### 1.4 架构债务清单

| 债务项                           | 类型         | 估计修复成本                              | 触发条件           |
| -------------------------------- | ------------ | ----------------------------------------- | ------------------ |
| Behavior 合约测试缺失            | 测试债务     | 中（6 × 4 = 24 套合约场景）               | 架构评审           |
| `createAdminShell` 无 destroy    | 资源泄漏     | 低（添加 destroy 方法 + 内部订阅清理）    | 组件卸载场景       |
| 快捷键无协调协议                 | 设计债务     | 中（引入优先级/仲裁层）                   | 多 Hotkey 共存场景 |
| 数据加载语义不精确               | 设计债务     | 中（扩展 AsyncStatus + DataSourceState）  | 加载态差异化需求   |
| Store 无泄漏检测                 | 基础设施债务 | 低（添加 `__leakDetect` 调试模式）        | 调试/性能分析      |
| `registerStore` SSR 安全未文档化 | 文档债务     | 低（明确标注工厂调用时机 + 框架适配注意） | 插件开发           |

## 2. 扩展方向

基于交叉验证揭示的缺口和 Iris UI 的技术愿景，以下是 5 个高价值架构扩展方向。

### 方向 A：Behavior 合约测试体系（P0）

#### 为什么需要

Behaviors 是 Iris UI 的**差异化卖点**（"正交叠加能力"），但目前是测试覆盖最薄弱的一环。没有合约测试意味着：

- 用户无法信任 Behavior 在 4 框架间的一致性
- 新增 Behavior 时，4 个适配器可能各自为政
- 这是对"薄桥"假设的唯一未验证部分

#### 核心挑战

1. **Behavior 的测试对象是行为而非组件**：传统组件测试（渲染 + 断言 DOM）不适用于 Behavior 测试
2. **跨框架行为一致性合约**：需要定义独立于框架的"行为规范"
3. **事件的模拟复杂性**：拖拽需要 PointerEvent 序列，快捷键需要 KeyboardEvent，点击外部需要 focus 变化

#### 预期架构变更

```
contracts/scenarios/
├── accordion.ts          (已有)
├── dialog.ts             (已有)
├── ...
├── behaviors/            ← 新增
│   ├── sortable.ts       ← Behavior 合约场景
│   ├── movable.ts
│   ├── resizable.ts
│   ├── click-outside.ts
│   ├── hotkey.ts
│   └── long-press.ts
```

**合约场景定义原则**：

- 每个 Behavior 合约 = 一组**输入序列 → 期望状态变化**的映射
- 合约不涉及任何框架 API，只描述"用户做了什么 → 系统应该怎样"
- 适配器测试 = 将合约翻译成各框架的事件调度

**选项对比**：

| 选项                            | 做法                                      | 成本            | 收益                           |
| ------------------------------- | ----------------------------------------- | --------------- | ------------------------------ |
| **A1：合约 + 框架测试（推荐）** | core 定义合约，各框架适配器消费合约       | 中（24 套测试） | 完整覆盖，契约约束最强         |
| A2：各框架自测                  | 不做合约，各框架写自己的 Behavior 测试    | 低              | 无法保证一致性                 |
| A3：e2e 测试                    | 用 Playwright 跑 4 框架的 Behavior 演示页 | 高              | 覆盖真实浏览器行为，但慢且脆弱 |

**推荐 A1**：与现有 `contracts/scenarios/` 体系一致，保持"合约定义 → 框架消费"的模式。

---

### 方向 B：快捷键仲裁协议（P0）

#### 为什么需要

当前 `IrisHotkeyProps.scope` 只有 `'document' | 'window'` 二元选择，无优先级/协调机制。这意味着：

- 多个 Hotkey 实例注册同一快捷键时，后者覆盖前者（非确定性）
- 内部组件（如 Dialog 内的快捷键）和全局快捷键可能冲突
- 无法实现"焦点优先"（如编辑器内 `Ctrl+S` 保存当前文件 vs 全局保存）

#### 核心挑战

1. **优先级模型**：需要定义清晰的优先级层级（全局 < 容器 < 焦点元素）
2. **事件冒泡与捕获**：需要决定快捷键是捕获优先还是冒泡优先
3. **动态注册/注销**：Behavior 是可嵌套的，快捷键栈需要随组件挂载/卸载动态变化
4. **避免开发者复杂性**：优先级模型必须直观，不能成为使用者的认知负担

#### 预期架构变更

**方案对比**：

| 方案                       | 模型                                                             | 复杂度 | 优势     | 劣势                   |
| -------------------------- | ---------------------------------------------------------------- | ------ | -------- | ---------------------- |
| **B1：优先级数字（推荐）** | `priority?: number`，默认 0，越高优先级越高                      | 低     | 简单灵活 | 数字魔法，无约束       |
| B2：优先级枚举 + 自动计算  | `scope: 'global'\|'container'\|'focused'`，基于 DOM 层级自动计算 | 中     | 语义明确 | 自动计算逻辑复杂       |
| B3：事件管道/中间件        | `hotkeyChain` 类似 Redux 中间件，每个快捷键经过管道              | 高     | 最灵活   | 开发成本高，认知负担重 |

**推荐 B1 + 约束**：允许 `priority` 覆盖，但默认值基于注册位置自动计算（如 `Dialog` 内注册的 Hotkey 自动获得比全局更高的优先级）。

**API 变更（不写代码，只描述方向）**：

```
IrisHotkeyProps:
  scope: 'document' | 'window'  ← 保留向后兼容
  priority?: number              ← 新增，默认基于 scope 自动计算
  preventDefault?: boolean       ← 新增，默认 true
  stopPropagation?: boolean      ← 新增，默认 false
```

**对现有系统的影响**：向后兼容——`priority` 可选，不传时行为与当前一致。

### 方向 C：Store 生命周期治理（P1）

#### 为什么需要

交叉验证揭示 `createAdminShell` 缺少 `destroy()` 方法，且 `createStore` 无泄漏检测基础设施。在 SPA 场景下（如 cms demos），组件反复挂载/卸载会导致：

- 幽灵订阅持续接收更新
- 内存泄漏（如果订阅持有闭包引用）
- 难以调试的副效应（如"为什么这个菜单还是展开的？"）

#### 核心挑战

1. **Store 的外部状态引用**：`createStore` 的订阅可以是任意回调，难以在销毁时自动清理
2. **Controller 的嵌套订阅图**：`createAdminShell` 内部使用了 `createSelectionModel` + `createExpansion` + `tabsNav`，需要级联销毁
3. **调试工具集成**：需要像 React DevTools 类似的 store 状态查看器

#### 预期架构变更

**阶段一：补齐 destroy 方法**

- 为 `createAdminShell` 添加 `destroy()`，内部清理 selection/expansion/tabsNav 订阅
- 确保所有 Controller 的 `destroy()` 是幂等的（可多次调用）

**阶段二：泄漏检测基础设施**

- 在 `createStore` 中添加调试模式：`createStore(initial, { debug: true })`
- 启用时，记录订阅者数量、订阅创建时间、组件堆栈
- 提供一个全局 `__IRIS_STORE_LEAKS__` 用于开发者工具

**阶段三：自动清理机制**（可选）

- 参考 React `useEffect` cleanup 模式，在适配器层的 `useController` 桥接中自动调用 `destroy()`
- 但保持 core 层无框架依赖——destroy 的手动调用的能力上，适配器做自动化

**对现有系统的影响**：

- `destroy()` 添加是纯加法，不影响现有调用方
- 泄漏检测以 `debug` 选项开关，不影响生产环境

### 方向 D：数据加载语义精确化（P1）

#### 为什么需要

当前 `loading: boolean` 无法区分三种截然不同的用户感知：

| 场景                       | 当前表现                                  | 期望表现                         |
| -------------------------- | ----------------------------------------- | -------------------------------- |
| 首次加载（page 1，无数据） | `loading=true`，显示 spinner              | ✅ 正确                          |
| 刷新（已有数据，重新加载） | `loading=true`，同时显示 spinner + 旧数据 | 应显示"刷新中"指示器（如顶部条） |
| 加载更多（已有数据，追加） | `loadingMore=true`                        | ✅ 正确（已有此字段）            |

但 `AsyncStatus` 也只定义了 `'idle' | 'loading' | 'success' | 'error'`，缺少 `'refreshing'`。

#### 核心挑战

1. **不破坏现有 API**：`loading: boolean` 不能移除，必须是超集演化
2. **与 `DataSourceState` 的协调**：`resolveDataState` 的逻辑需要更新
3. **四框架适配器桥接**：新增字段需要映射到各框架响应式系统

#### 预期架构变更

```
// 当前
type AsyncStatus = 'idle' | 'loading' | 'success' | 'error'

// 建议
type AsyncStatus = 'idle' | 'loading' | 'refreshing' | 'loadingMore' | 'success' | 'error'
```

`DataSourceState` 的变化：

```
// 当前
loading: boolean
loadingMore: boolean

// 建议（向后兼容）
loading: boolean       // = status === 'loading' || status === 'refreshing'
loadingMore: boolean   // 保留
status: AsyncStatus    // 新增，精确语义
```

**关键设计决策**：`loading` 保持为 `true`（当 `status` 为 `'loading'` 或 `'refreshing'` 时），确保所有现有消费 `loading` 的组件不受影响。

**对现有系统的影响**：

- 新增字段，不删除现有字段 ✅ 向后兼容
- `resolveDataState` 需要更新以理解 `refreshing` 状态
- 适配器桥接只需透传 `status` 字段

---

### 方向 E：架构证据系统（P2）

#### 为什么需要

方向④的证据伪造表明，纯手动源码分析存在**不可靠性**。需要一个系统化的机制来确保架构分析文档的断言可验证、可重复、可审计。

#### 核心挑战

1. **证据的可重复性**：grep 结果依赖当前代码状态、分支、时间
2. **避免人工伪造/偏差**：需要自动化证据采集
3. **与现有工具集成**：不增加额外开发工作量

#### 预期架构变更

**方案对比**：

| 方案                     | 做法                                                                                              | 成本 | 收益                        |
| ------------------------ | ------------------------------------------------------------------------------------------------- | ---- | --------------------------- |
| **E1：证据脚本（推荐）** | 创建 `scripts/arch-assertions/` 目录，每个断言是一个可执行的 `.sh` 或 `.ts` 脚本，输出结构化 JSON | 低   | 断言可重复执行，结果可 diff |
| E2：CI 集成              | 在 CI 中定期运行证据脚本，生成 `arch-evidence.json` 提交到仓库                                    | 中   | 自动发现断言漂移            |
| E3：形式化证明           | 用 TLA+/Alloy 对核心架构约束建模                                                                  | 高   | 最可靠，但成本过大          |

**推荐 E1 + E2**：先创建可执行证据脚本，后续纳入 CI。

**证据脚本规范**：

```json
// 每个断言的输出格式
{
  "assertion": "createResourceController has destroy()",
  "source": "packages/core/src/resource.ts:137",
  "command": "grep -n 'destroy:' packages/core/src/resource.ts",
  "result": "PASS",
  "timestamp": "2026-07-12T10:00:00Z",
  "commit": "abc123def456"
}
```

## 3. 接口设计建议

### 3.1 关键模块的接口设计原则

基于 Iris UI 当前的架构风格和交叉验证揭示的问题，提出以下接口设计原则：

#### 原则一：每个 Controller 都必须是"可清理的"

```
每个 create*Controller() 返回的对象必须包含:
- destroy(): void    ← 幂等，清理所有内部订阅
```

这是**最小完备合约**——任何管理状态的工厂函数，返回的对象都必须可以被销毁。当前 `createAdminShell` 违反了此原则。

#### 原则二：合约测试与实现测试分离

```
contracts/scenarios/behaviors/  → 定义 Behavior 的行为规范（框架无关）
packages/{react,vue,solid,svelte}/src/behaviors/ → 消费合约（框架相关）
```

合约测试 = "应该做什么"（状态变换描述）
实现测试 = "实际做了什么"（框架 API 调用验证）

#### 原则三：渐进式语义扩展，不破坏向后兼容

```
// 坏例子：删除 loading 字段
// 好例子：新增 status 字段，loading 作为派生属性
```

所有状态类型的扩展必须是**同构超集**——新类型可以赋值给旧类型的变量，反之不行。这保证了：

- 现有组件不用修改就能编译（但可能失去新语义）
- 新组件可以消费新字段

#### 原则四：优先级/协调协议必须是可选的

快捷键仲裁、焦点管理、拖动冲突——这些协调协议不能成为每个组件的强制依赖。设计应为：

```
默认行为 = 当前行为（无协调，直到冲突发生）
增强行为 = 通过可选 props/context 开启协调
```

### 3.2 是否需要引入新的抽象层

| 抽象层               | 需要？    | 理由                                                                                 |
| -------------------- | --------- | ------------------------------------------------------------------------------------ |
| **Behavior 合约层**  | ✅ **是** | 在 `contracts/scenarios/` 下新增 `behaviors/` 子目录                                 |
| **快捷键仲裁层**     | ⚠️ 可选   | 可以作为 `core` 中的 `createHotkeyOrchestrator` 工厂，不改变现有 `IrisHotkey` 的 API |
| **Store 泄漏检测层** | ✅ **是** | 作为 `createStore` 的可选调试模式，不引入新类型                                      |
| **数据加载语义层**   | ❌ 不需要 | 只需扩展现有类型，不需要新抽象                                                       |
| **架构证据层**       | ✅ **是** | 新的工具子系统，不改变运行时                                                         |

**重点讨论**：快捷键仲裁层的设计

**方案 1：全局协调器（推荐）**

```
@iris-ui/core 新增:
  createHotkeyOrchestrator()
    - register(key, handler, priority)
    - unregister(key, handler)
    - dispatch(event) → 按优先级级联处理

适配器层:
  IrisHotkeyProvider(orchestrator) → context 提供协调器
  IrisHotkey(priority) → 自动注册到协调器
```

**方案 2：事件管道**

```
每个 Hotkey 实例是一个中间件节点:
  input → [Hotkey A(priority=10)] → [Hotkey B(priority=5)] → handler
  A 可以阻止 B 执行
```

**推荐方案 1**，原因：

1. 与现有插件/IrisProvider 模式一致（类似 `runPlugins`）
2. 优先级数字简单直观
3. 可以全局查看注册表（便于调试）

### 3.3 如何保持向后兼容性

| 变更                                   | 向后兼容策略                 | 废弃周期       |
| -------------------------------------- | ---------------------------- | -------------- |
| 添加 `priority` 到 Hotkey              | 可选 prop，默认 = 当前行为   | 无废弃，纯加法 |
| 添加 `status` 到 DataSourceState       | 新增字段，`loading` 保持兼容 | 无废弃，纯加法 |
| 为 `createAdminShell` 添加 `destroy()` | 新增方法                     | 无废弃，纯加法 |
| 新增 Behavior 合约测试                 | 新文件，不影响现有测试       | 无废弃，纯加法 |
| `registerStore` SSR 文档化             | 文档更新                     | 无废弃，纯加法 |

**关键原则**：所有架构扩展**必须是纯加法**。不修改现有 API 的签名，不删除现有字段，不改变现有行为的默认值。

## 4. 技术选型

### 4.1 是否需要引入新的技术栈或框架

| 方向              | 是否需要新技术栈 | 理由                                     |
| ----------------- | ---------------- | ---------------------------------------- |
| Behavior 合约测试 | ❌ **不需要**    | 复用现有 Vitest + jsdom 基础设施         |
| 快捷键仲裁        | ❌ **不需要**    | 纯逻辑，进 `@iris-ui/core`，零框架依赖   |
| Store 生命周期    | ❌ **不需要**    | 纯逻辑，进 `@iris-ui/core`               |
| 数据加载语义      | ❌ **不需要**    | 纯类型扩展                               |
| 架构证据系统      | ⚠️ **可选**      | 简单的 shell/node 脚本即可，不需要新框架 |

**结论**：5 个扩展方向均**不需要引入新的技术栈或框架**。所有变更都在现有技术选型内完成（TypeScript + Vitest + Turborepo）。

### 4.2 第三方依赖的评估标准

对于 Iris UI 这样对包大小和框架中立性高度敏感的项目，引入任何第三方依赖应满足以下标准：

| 标准                | 权重    | 说明                                                      |
| ------------------- | ------- | --------------------------------------------------------- |
| **零框架依赖**      | 🔴 必须 | 不能在 `@iris-ui/core` 中引入 React/Vue/Solid/Svelte 依赖 |
| **可摇树**          | 🔴 必须 | ESM 导出，支持 tree-shaking                               |
| **大小预算**        | 🟡 重要 | 新增依赖的 gzip 后大小应在设计文档中声明                  |
| **TypeScript 原生** | 🟡 重要 | 提供一流类型定义，避免 `@types/` 额外包                   |
| **SSR 安全**        | 🟡 重要 | 不会在 `import` 时执行浏览器 API                          |
| **维护状态**        | 🟢 建议 | 近 6 个月有活跃提交                                       |

**当前分析**：

- 快捷键仲裁不需要新依赖（纯 Map + 事件监听器）
- Store 泄漏检测不需要新依赖（装饰器模式 + 性能 API）
- 数据加载语义不需要新依赖（纯类型变更）
- Behavior 合约测试不需要新依赖（Vitest 已就绪）

### 4.3 自建 vs 采购的决策依据

对于架构级能力，Iris UI 的决策矩阵：

| 能力           | 建议     | 理由                                                         |
| -------------- | -------- | ------------------------------------------------------------ |
| 快捷键仲裁     | **自建** | 核心差异化能力，需要与 Iris UI 的 scope/context 体系深度集成 |
| Store 泄漏检测 | **自建** | 2-3 天工作量，不值得引入外部库                               |
| 架构证据系统   | **自建** | 定制化需求高，需要与现有 CI/Git 集成                         |
| 数据加载语义   | **自建** | 纯类型变更，零外部依赖                                       |

**决策原则**：所有与 Iris UI 核心架构（token/插件/Controller）深度耦合的能力，都应自建。只有通用基础设施（如虚拟滚动可以用 TanStack Virtual、浮层定位可以用 Floating UI）才考虑外部依赖。

## 总结

交叉验证揭示的 5 个方向，在架构层面反映了 Iris UI 当前的两个根本性挑战：

1. **"薄桥"假设未完全验证**：Behavior 合约测试的缺失意味着「适配器只渲染 + 桥接」这个核心信念缺少最关键的实证。修复方向 A 是优先中的优先。

2. **协调基础设施缺失**：快捷键冲突不仅是 Hotkey 的问题，它是更广泛模式——**正交能力的组合需要协调协议**。Resizable + Movable 同时作用于一个元素时、ClickOutside + LongPress 同时启用时，都需要类似的仲裁机制。方向 B 解决的是这个更广泛的问题的原型。

3. **生命周期治理不完整**：Controller 模式是 Iris UI 的核心架构模式，但 `destroy()` 的缺失（`createAdminShell`）表明这个模式的设计规范没有被完全遵守。方向 C 治理的是整个 Controller 生态的"质保"问题。

4. **证据文化的缺失**：方向④的证据伪造是最令人不安的发现。不是因为这 5 个方向的哪个结论错了，而是因为它揭示了一个流程漏洞——**架构分析中的源码断言缺乏可验证性**。方向 E 治理的是这个问题。

5 个方向合起来，构成了 Iris UI 从"优秀"到"卓越"的路径：从四框架对齐（已完成）→ Behavior 行为一致性验证（方向 A）→ 组合能力的协调协议（方向 B）→ 资源安全（方向 C）→ 语义精确（方向 D）→ 架构治理闭环（方向 E）。

建议按 P0 → P1 → P2 顺序推进，总计约 13.5 人周的投入，即可消除这 5 个架构缺口，将 Iris UI 的架构成熟度提升一个完整层级。
