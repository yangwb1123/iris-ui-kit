# 安全审查：Iris UI

## 总体安全态势：良好 — 存在可控风险

### 架构强度

Iris UI 的架构设计具有**良好的安全基础**：

| 良好实践                      | 证据                                                                                                                                                           |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **无 innerHTML 默认渲染**     | 所有四个框架的图标组件都使用 `createElement` / `h()` / `<svelte:element>` / `<Dynamic>` 渲染 SVG 节点。`IrisIcon`（React）显式省略 `dangerouslySetInnerHTML`。 |
| **无 eval / Function 构建器** | 整个代码库中 grep 无结果。                                                                                                                                     |
| **textContent 用于样式注入**  | `skinBootScript` 使用 `textContent`（注释："never innerHTML"）。`injectGlobalStyles` 也使用 `textContent`。                                                    |
| **输出转义**                  | `toCsv` / `toHtml` / `toSpreadsheetXml` 中的所有导出路径都使用适当的转义（`escapeXml`、CSV 引用）。                                                            |
| **受控的插件系统**            | 插件严格**附加**：它们可以注册 tokens / messages / stores，但不能打补丁现有组件、不能注册动态组件、不能覆盖核心逻辑。                                          |
| **输入验证**                  | `validateSkin` 在加载和执行之前检查 token 类型、key 格式、类型值。                                                                                             |
| **SSR 安全**                  | 所有基于 DOM 的操作在 SSR 期间都是无操作的（`typeof document === 'undefined'` 守卫）。                                                                         |

### 发现 #5：皮肤 JSON 解析使用 `JSON.parse`（无 reviver）且 token 值未经过滤

| 字段         | 描述                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **类别**     | 输入验证                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **严重性**   | 🟡 **中等**                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **标题**     | 皮肤 `JSON.parse` 可能允许 prototype 污染通过自定义 token 值                                                                                                                                                                                                                                                                                                                                                                 |
| **位置**     | `packages/skins/src/loadSkin.ts`（第 28 行：`await res.json()`）；`packages/skins/src/validateSkin.ts`（第 40–72 行）                                                                                                                                                                                                                                                                                                        |
| **描述**     | `loadSkin` 从 JSON 解析皮肤，不带 `reviver` 函数。解析后的对象被传递给 `validateSkin`，它检查 `custom` 键的 `DOT_KEY` 正则表达式 `/^[a-zA-Z][\w-]*(\.[a-zA-Z][\w-]*)*$/` —— 这排除了 `__proto__`（以 `_` 开头）和 `constructor`（以 `c` 开头，但在 `[a-zA-Z]` 范围内）—— 所以验证器确实阻止了典型的 prototype 污染键。检查是**足够的**，但假设验证器被正确调用。如果代码路径绕过验证器，原始的 `Skin` 对象可能包含危险的键。 |
| **攻击场景** | 如果在皮肤加载路径的未来重构中，验证器被省略或 `loadSkin` 被改为直接传入原始对象而不验证，攻击者可以提供 `{"custom": {"__proto__": {"isAdmin": true}}}` 来污染所有对象的 `Object.prototype`。                                                                                                                                                                                                                                |
| **影响**     | 可能通过复杂对象赋值的 prototype 污染导致绕过授权检查、属性注入。                                                                                                                                                                                                                                                                                                                                                            |
| **建议**     | 1. 添加防御性 `JSON.parse(text, reviver)` 调用，显式阻断 `__proto__` 和 `constructor` 键。2. 添加一个集成测试，验证 `loadSkin` 拒绝 prototype 污染载荷。                                                                                                                                                                                                                                                                     |
| **工作量**   | S（< 1 天）：添加 reviver + 测试。                                                                                                                                                                                                                                                                                                                                                                                           |

| **描述**     | `orderPlugins` 在其 DFS 中正确检测循环并通过 `devWarn` 报告它们。然而，如果插件被交换（通过 `reloadPlugins`），`destroy()` 方法可能抛出异常。destroy 错误被隔离（一个不会阻塞另一个），但 `reloadPlugins` 对每个被移除的插件调用 `destroy()`，然后运行 `runPlugins(next)`。如果一个 `destroy()` 抛出一个异步错误（在捕获中被吞噬），下次加载相同插件时可能会留下残留状态。 |
| **攻击场景** | 一个包含具有破坏性 `destroy()` 的恶意插件的插件集被动态移除。Destroy 抛出一个错误（被捕获）。旧的监听器/状态可能仍然存在。重新添加插件时可能会得到陈旧的数据。影响有限。                                                                                                                                                                                                   |
| **影响**     | 在动态插件重载后微妙的状态泄漏。                                                                                                                                                                                                                                                                                                                                           |
| **建议**     | 1. 添加一个测试，验证 `reloadPlugins` 在 `destroy()` 抛出后仍然产生干净的注册状态。2. 确保在销毁错误后重置存储状态。                                                                                                                                                                                                                                                       |
| **工作量**   | S（< 1 天）：添加测试 + if 守卫。                                                                                                                                                                                                                                                                                                                                          |

## 结论

Iris UI 拥有一个**核心架构良好的安全姿态**，这要归功于其不使用 `innerHTML`、不依赖 `eval`、以及结构化的插件系统。主要的攻击面不是核心库，而是**plugin-markdown 插件**，它在净化为 HTML 输出时使用基于正则表达式的净化，会直接进入 `dangerouslySetInnerHTML`。这是最关键的问题。

次要问题涉及**通过皮肤加载的 SSRF**（在 Node.js/Tauri 环境中）和**资源获取中的竞态条件**（数据完整性 + DoS）。两者都有简单的缓解措施。

该库在 XSS 方面明显优于大多数 UI 库，因为其架构禁止了原始的 innerHTML 注入，并且其所有四个适配器的图标渲染都避免使用 svg innerHTML。主要的发现是**可修复的**并且是**局部的**。
