## 2. 测试策略

### 测试金字塔

```
        ╱  E2E  ╲          ← 完全缺失！
       ╱──────────╲
      ╱ Integration ╲      ← 合约测试 + 一些表单集成测试
     ╱────────────────╲

   ╱──────────────────────╲
```

**问题：** 缺乏 E2E 层。没有 Playwright、Cypress 或任何浏览器自动化测试。没有视觉回归测试。

### 合约测试（跨框架）

跨框架合约测试系统是一个**重大优势**。`@iris-ui/core/contracts` 定义了 40+ 个场景（`switchScenario`、`tabsScenario`、`tableSortScenario` 等），每个框架的 `contracts.test.tsx` 运行这些场景，验证跨框架行为一致性。这验证了适配器架构。

### SSR 测试

React 和 Vue 有正确的无 DOM SSR 测试（`// @vitest-environment node`），验证：

- 无渲染时 DOM 访问
- 确定性 ID（不会出现计数器漂移）
- ARIA 关联完整性

**问题：** Solid 和 Svelte 缺少 SSR 测试。

## 3. 测试质量

### 优势

- **确定性计时：** 使用 `fakeScheduler()` 处理超时/间隔，避免真实计时器并消除 jsdom 的不确定性
- **竞态条件保护：** `deferred()` 用于表单验证、异步资源和数据源加载中的竞态条件测试
- **无框架依赖：** Core 包测试验证了 0 个框架导入（`from 'react'` / `from 'vue'` 等）
- **清晰的断言：** 测试使用集中的 `expect()` 断言——没有模糊的匹配器
- **可访问性门控：** axe-core 在所有 4 个框架中集成，使用 WCAG 2.0/2.1 A & AA 规则

### 问题

1. **无代码覆盖阈值：** 没有 `vitest.coverage` 配置。没有覆盖收集，没有差异覆盖门控。
2. **无快照测试：** 没有 `__snapshots__` 目录。SSR 输出测试手动断言，可能遗漏细微的变化。
3. **Svelte 测试从 dist 编译：** Svelte 测试针对编译后的输出（`dist/` 或 `.svelte-kit/`）运行，而不是源文件。这调试起来更慢、更困难。
4. **有限的模拟管理：** 没有用于 localStorage、matchMedia、ResizeObserver 的集中模拟设置——这些在单独的测试文件中重复出现。

## 6. 测试基础设施

### CI/CD 集成

质量门：`pnpm turbo run test typecheck lint build`（4 道门）+ `pnpm size` + `pnpm check:rsc` + `pnpm format:check`

**优势：**

- Turborepo 缓存加速重运行
- Husky + lint-staged 用于提交前格式化
- Changesets 用于版本控制
- 架构检查（`arch-check.mjs`）与基线棘轮机制

**差距：**

- 无覆盖门控（见发现 #2）
- 无差异覆盖检查（仅分支水平的基线覆盖）
- 无 CI 基准测试回归检测
- 无并行测试执行限制（由于 jsdom 限制）

### 测试数据管理

- 测试数据是内联定义的——在单个文件中，每个套件有 3-5 行。没有共享数据工厂或生成器。
- 没有测试数据种子脚本。
- 没有外部测试夹具管理。

### 测试工具/辅助函数

所有框架都有可重用的模式：

- `deferred()` 用于异步/竞态条件测试
- `fakeScheduler` 用于基于计时的测试
- 每个套件使用 `afterEach(() => cleanup())` 进行清理
- 合约场景驱动跨框架测试

**差距：**

- 没有用于 DOM 模拟的共享测试工具（matchMedia、ResizeObserver、IntersectionObserver）
- 没有用于弹出窗口/工具提示/弹出器的共享浮动定位模拟

## 8. 最终总结

### 整体测试健康度：良好 (Good)

Iris UI 拥有一个**异常强大的单元测试基础**，具有深思熟虑的架构，支持跨框架合约测试、SSR/SSR 守护、可访问性验证、架构自动化检查以及性能基准测试。测试质量高——确定性、无框架依赖、清晰的断言，并覆盖了竞态条件和状态转换等复杂的边缘情况。

### 发布前的关键测试差距

| #   | 差距                                              | 严重性 | 工作估算               |
| --- | ------------------------------------------------- | ------ | ---------------------- |
| 1   | **无 E2E 测试**（Playwright）— 浏览器回归透明     | 严重   | 中等（3-5 天初始边界） |
| 2   | **无测试覆盖工具** — 无法量化的覆盖缺口           | 严重   | 小（半天配置 vitest）  |
| 3   | **缺少 Solid/Svelte SSR 测试** — SSR 回归可能逃逸 | 高     | 小（1 天移植）         |
| 4   | **缺少 XSS 安全测试** — 用户内容向量未测试        | 高     | 小（半天添加断言）     |

### 测试策略改进

1.  **实现测试金字塔**：添加 E2E 层（Playwright），重点放在关键用户路径上：CMS CRUD 操作、主题切换、表格操作。从 10 个测试开始，然后扩展。

2.  **启用覆盖门控**：配置 vitest 覆盖并添加增量差异覆盖到 CI。将覆盖阈值设定得现实（开始时 branches: 70, functions: 80，然后收紧）。

3.  **标准化跨框架测试质量**：Svelte 和 Solid 测试密度应匹配 React/Vue。在 CI 中为适配器添加最低每组件测试行数门控。

4.  **合约测试驱动开发**：核心中有 ~40 个场景——应确定优先级。新组件应包含合约场景，以确保跨框架行为一致。

### 快速取胜（高价值、低工作量）

1.  **向 vitest 配置文件添加覆盖**（~30 分钟）——立即揭示测试差距
2.  **将 React SSR 测试文件移植到 Solid 和 Svelte**（~1-2 小时）——捕获 SSR 回归
3.  **为以下组件添加 5-10 行测试**：Solid 和 Svelte 中的 `IrisSlot`、`IrisVisuallyHidden`、`IrisKbd`、（每个 ~5 分钟）——用最小的努力提升基线
4.  **添加 XSS 断言到 Input 和 Textarea 测试**（~30 分钟）——涵盖一个现实的安全风险
5.  **在 CI 中启用 `test:coverage` 脚本**作为门控，带着警告模式开始（~1 小时）——提高可见性

### 测试技术债务

- 138 个测试文件少于 50 行（主要通过 Svelte 和 Solid 分布在简单的展示组件中）
- 无快照测试（对纯组件安全——为 SSR 输出、CSS Var 生成添加）
- Svelte 测试从编译后运行，而不是从源文件运行——修复以支持更好的调试
- 无结构化的测试数据工厂——在大型测试中导致重复
- 存储/皮肤测试在失败场景中模拟 `localStorage` 不够全面
