> **分析依据**：项目 AGENTS.md（完整架构文档）、事实核查验证报告（五大方向审查结果）
> **分析人角色**：资深架构师
> **分析日期**：2026-07-12

## 1. 架构评估

### 1.1 当前架构优势

**四框架对齐是核心资产，而非附带品。** 从架构角度看，Iris UI 已经做到了许多 UI 库未能做到的事：**逻辑与渲染的严格解耦**。

| 优势维度   | 评估    | 说明                                             |
| ---------- | ------- | ------------------------------------------------ |
| 分层纯度   | 🟢 极强 | Layer 0（core）无框架依赖，四适配器只做桥接渲染  |
| A/B/C 分类 | 🟢 极强 | 是"逻辑放哪"的显式决策树，防架构退化             |
| 标准化程度 | 🟢 强   | 命名、子路径、机器事件、CSS var 均有统一约定     |
| 质量门禁   | 🟢 强   | 四道门 + size + RSC + format + arch-check 全自动 |
| 渐进复杂度 | 🟢 强   | Button 可起步，插件按需 use                      |
| 跨框架一致 | 🟢 极强 | 149 组件四框架同名同语义，manifest 验证          |

**关键设计决策合理性审查：**

| 决策                                             | 评判    | 理由                                              |
| ------------------------------------------------ | ------- | ------------------------------------------------- |
| 状态机只用于有事件语义的组件                     | ✅ 正确 | 防止 svjs 退化（400 行 machine 覆盖一个 boolean） |
| 选择/展开用 createSelectionModel/createExpansion | ✅ 正确 | 被 17+ 组件复用，证明抽象有效                     |
| 插件不提供 registerComponent                     | ✅ 正确 | 保留类型安全 + tree-shaking + manifest 自动化     |
| 皮肤继承 + 自定义命名空间                        | ✅ 正确 | 运行时解析为完整 IrisTheme，组件零改动            |
| 适配器只渲染+桥接                                | ✅ 正确 | 四框架对齐 149 组件为证                           |

### 1.2 当前架构局限性

> 这部分不是"缺陷"，而是**架构目前未覆盖的维度**，也是五大方向存在的前提。

**局限 1：运行时正确性依赖人工 + 编译时检查，缺少运行态契约验证。**

当前质量门覆盖：test（黑盒）、typecheck（类型）、lint（风格）、build（构建）、size（体积）。但**跨框架的运行时一致性**无自动化保障——同一组件在 React 里展开行为正确，在 Svelte 里是同一逻辑路径吗？目前靠单元测试各自覆盖，缺少**统一的行为规范录**。

**局限 2：数据管线（filter→sort→paginate→fetch）的可观测性为零。**

`createResourceController` 是核心数据管线，但它内部的 filter 变更→sort 重置→page 回 1→refetch 的因果链是**隐式状态图**。当前无法在 devtools 中追踪"为什么发起了这个请求"、"哪一层取消了上一个请求"。

**局限 3：Singleton SSR 安全无系统性保障。**

AGENTS.md 明确列出"共享单例须 afterEach 重置"（scroll-lock计数/toast队列/globalStore），但这只是测试约束，**不是架构级防御**。每个新 singleton 的开发者必须自己记住这条规则。事实核查已发现 Svelte toast 适配器可能存在同样问题——说明这不是理论风险，而是已发生的架构缺口。

**局限 4：突变测试作为质量门缺位。**

~1500 测试四道门全绿，但**测试的有效性**未知。1 个测试可以 assert 10 个无关的东西而通过——这种"误绿"不会被任何质量门捕住。突变测试是验证测试"真的在测逻辑"的唯一方式。

**局限 5：跨框架行为一致性无量化门禁。**

当前"对齐"靠：同一组 core 控制器 + 各自适配器的单元测试。但**没有统一的场景定义**来声明"在 4 个框架中，这个交互的语义应该完全相同"。导致适配器可能各自对 core 的回调时机、状态扁平化方式有细微差异。

### 1.3 架构债务 / 技术债

**中等优先级债务：**

1. **子路径 exports 手动维护**：每个包在 `package.json` 的 `exports` 字段需要手动列出子路径（`@iris-ui/react/form` 等）。已有 manifest 扫描 barrel，但 exports 字段未自动化——新增子组件时容易漏掉。

2. **插件包构建三工具链**：`tsup` 数组配置 + `svelte-package` + 三套 vitest 配置串行。构建编排复杂度高，新入门的插件作者需要理解三套配置才能贡献。

3. **事实核查报告中 48→42 的偏差**：说明文档与实践之间有 6 个合约场景的 gap——可能是文档过期、或测试未覆盖。无论哪种，都是文档-代码一致性的债。

**低优先级债务：**

4. **solid/svelte 适配器的 Svelte 5 rune 兼容**：AGENTS.md 提到 `$state` 命名冲突问题，这需要持续关注 Svelte 演进。

5. **皮肤市场 SDK 的接口稳定**：可加载皮肤（`extends` 继承 + 自定义命名空间）已定义，但"市场 SDK"（外部皮肤作者工具链）尚未第一个外部消费者验证接口稳定性。

## 2. 扩展方向

### 方向 ① 运行时契约验证系统（P0）

**为什么需要**

当前架构缺少**框架无关的组件行为定义层**。每个适配器的测试各自验证"组件应该打开/关闭"，但没有一处声明"`IrisPopover` 在收到 `OPEN` 事件后应设置 `open=true` 并触发 `onOpenChange(true)"`。这个行为的定义是隐含的、分散的、靠自己读源码拼凑的。

**业务价值**：

- 减少跨框架行为漂移（同一组件在 React 能打开、Svelte 打不开）
- 新人接手新框架适配器时，有明确的"必须实现的场景清单"
- AI 消费层（`llms.txt`）可自动生成精确的行为文档

**技术价值**：

- 可作为 mutation testing 的"正确性 oracle"
- 可作为回归测试的基线

**核心挑战**

| 挑战           | 难度 | 说明                                             |
| -------------- | ---- | ------------------------------------------------ |
| 契约格式定义   | 中   | 需要表达"事件→状态转换→回调触发"序列，且框架无关 |
| 跨框架执行引擎 | 高   | 同一契约需在 jsdom + 4 框架渲染器中运行          |
| 异步时序       | 高   | 浮层动画、异步数据加载的时序不确定性             |
| 契约完备性判断 | 中   | 何时算"覆盖够了"——42 个合约场景够吗？            |

**预期架构变更**

```
   ┌──────────────────────┐
   │   @iris-ui/contracts  │  ← 新增包：框架无关的契约定义 + 运行时
   │                      │     场景是 YAML/TS 类型定义的交互规范
   │  defineContract({    │
   │    name: 'popover',  │
   │    scenarios: [      │
   │      { given:'closed', event:'OPEN', then:{ open:true, onOpenChange:[true] } }
   │    ]                 │
   │  })                  │
   └────────┬─────────────┘
            │ 消费
   ┌────────▼─────────────┐
   │  @iris-ui/core        │  集成到现有质量门
   │  + contract runner    │  但包本身无框架依赖
   └────────┬─────────────┘
            │ 桥接
   ┌────────▼─────────────┐
   │  react/vue/solid/svelte │  各适配器运行同一组契约
   │  + contract.verify()  │  CI 中 assert 4 框架结果一致
   └──────────────────────┘
```

**对现有系统的影响**

| 影响             | 程度 | 说明                                             |
| ---------------- | ---- | ------------------------------------------------ |
| break API change | 无   | 纯增量，不修改已有组件                           |
| 构建             | 低   | 新增一个包，不需要改现有构建链                   |
| 测试             | 中等 | 需要新增 CI 步骤（四框架契约检验），但测试量可控 |
| 文档             | 低   | 契约本身即文档                                   |

### 方向 ② 数据管线可观测中间件（P0）

**为什么需要**

`createResourceController` 是 Iris UI 中最复杂的状态机之一。它管理 filter→sort→paginate→fetch 的因果链。当前这个因果链是**黑箱**——开发者只能看 `loading` 和 `data` 两个输出，不知道"我改了 filter 后为什么发了请求"、"为什么 sort 变了但 page 没重置"。

**业务价值**：

- 调试 CRUD 页面的数据流（开发者体验）
- 理解"为什么多发了请求"（避免冗余网络开销）
- 性能分析（每次数据管线更新耗时）

**技术价值**：

- 中间件模式可复用到其他引擎（form、async、tabsNav）
- 可观测数据可用于自动化测试（验证"filter 变更 → page 重置"链发生）
- 为未来 devtools 扩展提供基础

**核心挑战**

| 挑战            | 难度 | 说明                                               |
| --------------- | ---- | -------------------------------------------------- |
| 中间件 API 设计 | 高   | 需要不破坏现有 createResourceController 的使用方式 |
| 性能开销        | 中   | 中间件链不能显著增加每次 state 更新的延迟          |
| 数据序列化      | 低   | 事件数据（filter 值、sort 字段）可能是复杂对象     |
| 隐私过滤        | 中   | 中间件可能暴露敏感数据（用户列表），需过滤机制     |

**预期架构变更**

```
  ┌─────────────────────────────────┐
  │ createResourceController        │
  │  current: 内部 .setFilter()     │ → data/loading/error
  │           → .resetPage()        │
  │           → .fetch()            │
  └─────────────────────────────────┘

  ┌─────────────────────────────────┐
  │ createResourceController        │
  │  + plugin: observableMiddleware │
  │  + middleware pipeline:         │
  │    setFilter → onBeforeFilter   │
  │             → resetPage         │
  │             → onBeforePageReset │
  │             → fetch             │
  │             → onAfterFetch      │
  │  emit: { type, payload, ts }    │
  └─────────────────────────────────┘
```

**中间件接入方式**（需决策）：

| 方案                 | 优点               | 缺点                                           |
| -------------------- | ------------------ | ---------------------------------------------- |
| A. 函数参数          | 无新增概念         | 需要改 createResourceController 函数签名       |
| B. 插件（usePlugin） | 与现有插件体系一致 | 需要中间件在 core 生命周期里有 hook 点         |
| C. EventEmitter      | 简单直接           | 不兼容现有"纯函数"模式，state 更新可能错过事件 |

**推荐**：方案 B（插件），因为 Iris UI 已有 `createPlugin`/`runPlugins` 机制。在 `createResourceController` 内部加一个可选的 `middleware` pipeline，插件系统注册监听器。`useResourceController` 桥接适配器时，若检测到 `devtools` 插件存在则激活中间件。

**对现有系统的影响**

| 影响             | 程度 | 说明                                             |
| ---------------- | ---- | ------------------------------------------------ |
| break API change | 无   | 中间件是可选参数                                 |
| 构建             | 低   | 无新增依赖                                       |
| 测试             | 低   | 中间件自身单测 + resourceController 集成测试不变 |
| 文档             | 低   | 新增"可观测性"章节                               |

### 方向 ③ Singleton SSR 安全协议（P0）

**为什么需要**

事实核查已发现 Svelte toast 适配器可能存在的 singleton SSR 问题。当前缺少**系统性防御**——每个共享单例（scroll-lock 计数、toast 队列、stylesheet 注入、皮肤引擎、`createStore`）依赖开发者自行遵守规则。

**业务价值**：

- SSR 场景不会因为共享状态而泄露用户数据（用户 A 看到用户 B 的 toast）
- 确保 hydration 一致
- 是生产就绪的必备条件

**技术价值**：

- 可复用为所有 singleton 的基类
- 减少"我忘了 reset"类 bug

**核心挑战**

| 挑战     | 难度 | 说明                                          |
| -------- | ---- | --------------------------------------------- |
| 无感接入 | 高   | 现有 singleton 开发者不需要理解复杂协议       |
| 自动检测 | 中   | 如何在 CI 中自动发现新 singleton 是否遵循协议 |
| 框架差异 | 中   | React/Vue 的 SSR 与 Svelte/Solid 不同         |
| 性能损耗 | 低   | 仅在 SSR 环境激活                             |

**预期架构变更**

```
  ┌──────────────────────┐
  │ createSafeSingleton  │ ← 新增 core 导出
  │                      │
  │ const toastQueue =   │
  │   createSafeSingleton│
  │   ('toast-queue',    │
  │    () => new Map())  │
  │                      │
  │ ● 自动检测环境       │
  │ ● SSR: 返回空实例    │
  │ ● 客户端: 返回真实   │
  │ ● afterEach reset    │
  └──────────────────────┘
```

**防御层次**（多层防御，而非单点）：

| 层次 | 方式                                    | 责任方       |
| ---- | --------------------------------------- | ------------ |
| L1   | `createSafeSingleton` 包装器            | core 提供    |
| L2   | CI lint rule（`no-raw-module-global`）  | ESLint 插件  |
| L3   | 契约场景覆盖（在 SSR 环境中打开 toast） | contracts 包 |

**对现有系统的影响**

| 影响             | 程度 | 说明                      |
| ---------------- | ---- | ------------------------- |
| break API change | 低   | 现有 singleton 可逐步迁移 |
| 构建             | 低   | 新增一个 core 导出        |
| 测试             | 低   | 需要 SSR singletion 测试  |
| 文档             | 低   | 新增 "SSR 安全" 章节      |

### 方向 ④ 跨框架行为保真度门禁（P1）

**为什么需要**

当前"跨框架一致"靠源码一致性（同一组 controllers）+ 人工 review。但没有**量化测量**。一个新 PR 改了 React 适配器的 toast 销毁逻辑——Solid 和 Svelte 适配器的行为会漂移吗？目前无法在 CI 中回答这个问题。

**业务价值**：

- 防止渐进式跨框架漂移（两周前都一样，两周后 React 和 Svelte 不同了）
- 新人可安全地只改一个框架而不破坏其他
- AI 生成的适配器代码可被自动验证

**技术价值**：

- 与方向①的契约系统互补：契约定义"应该怎样"，保真度告诉你"实际差多远"
- 可量化"框架成熟度"（React: 100% 保真度, Solid: 98%）

**核心挑战**

| 挑战           | 难度 | 说明                                                 |
| -------------- | ---- | ---------------------------------------------------- |
| 测量粒度       | 高   | "行为"比"渲染"更抽象——什么叫行为一致？               |
| 时序噪声       | 高   | 异步行为（setTimeout、animation frames）时序不确定性 |
| 跨框架渲染差异 | 中   | React 的合成事件 vs Svelte 的原生事件                |
| 保真度阈值设计 | 中   | 100% 是幻觉——有些差异是框架特性，不算 bug            |

**预期架构变更**

```
  ┌──────────────────────────┐
  │ 保真度测量工具           │
  │                          │
  │ 测量维度:                │
  │  1. 状态转换一致性       │ → 契约场景运行后各框架 state 一致
  │  2. 回调触发一致性       │ → 同一 event 触发同一回调序列
  │  3. 渲染输出一致性       │ → DOM 结构 + CSS 类名 + attr
  │  4. 时序一致性           │ → 同一事件序列后各框架状态相同
  │                          │
  │ 输出: fidelity score 0-1 │
  └──────────────────────────┘
```

**保真度 ≠ 100% 相同**。有些差异是合法的：

- React 的 `onChange` 时机与原生不同——这是 React 设计，不算 Iris UI 的 bug
- Svelte 的 `$effect` 执行顺序不同——框架特性

关键区别：**用户可见的行为差异**（popover 点不开）vs **内部实现差异**（事件处理方式不同）。

**对现有系统的影响**

| 影响             | 程度 | 说明                                      |
| ---------------- | ---- | ----------------------------------------- |
| break API change | 无   | 纯增量                                    |
| 构建             | 中   | 新增 CI 步骤（四框架同时运行 + 结果对比） |
| 测试             | 中   | 需要定义保真度测试框架                    |
| 文档             | 低   | 新增"保真度"指标                          |

---

### 方向 ⑤ 突变测试质量放大（P1）

**为什么需要**

~1500 测试，四道质量门全绿。但**测试的有效性**无人知道。一个测试的 assert 可能检查的是无关的属性，或者测试的 setup 覆盖不了真正出 bug 的路径。突变测试是通过**故意引入 bug** 来验证测试能捕住它。

**业务价值**：

- 知道"哪些代码是真正受保护的，哪些是假绿"
- 新增代码时知道"这个测试够不够"
- 减少线上 bug（被假绿骗过的回归测试）

**技术价值**：

- 可指导新增测试的写入方向（"这里突变杀不死，需要加测试"）
- 可识别"dead code"（突变不被任何测试覆盖的代码）
- 质量数据可用于"哪些模块需要重构"

**核心挑战**

| 挑战       | 难度 | 说明                                                       |
| ---------- | ---- | ---------------------------------------------------------- |
| 执行时间   | 高   | 突变测试是 N 倍于原始测试的时间                            |
| 阈值设定   | 中   | 什么是"通过"的 mutation score？80%？90%？                  |
| 假阳性处理 | 高   | 有些突变（如：把 if 条件取反）产生等价变异体，不可能被杀死 |
| 包范围选择 | 中   | 四包（core + 4 适配器）全部做？还是只 core？               |

**预期架构变更**

```
  ┌──────────────────────┐
  │ 突变测试场景          │
  │                      │
  │ 高价值目标(按事实核查) │
  │  ① store.ts          │ → 几乎全局所有状态管理依赖此处
  │  ② selection/        │ → 17 组件复用
  │  ③ expansion/        │ → 4 框架 NavMenu 共享
  │  ④ resourceController│ → CRUD 管线核心
  │  ⑤ form              │ → 表单系统核心
  │                      │
  │ 逐步扩展: core →     │
  │ 适配器桥接代码        │
  └──────────────────────┘
```

**集成方式**：不放在核心 CI 流程中（mutations 耗时太长），而是作为**定期质量审计**（nightly/weekly），在发现分数下降时报警。

**对现有系统的影响**

| 影响             | 程度 | 说明                                |
| ---------------- | ---- | ----------------------------------- |
| break API change | 无   | 纯增量，不影响运行时                |
| 构建             | 中   | 新增 nightly pipeline、Stryker 配置 |
| 测试             | 低   | 现有测试不变，只新增 meta 验证      |
| 文档             | 低   | 新增"测试质量"章节                  |

## 3. 接口设计建议

### 3.1 关键模块的接口设计原则

**原则 1：契约包的设计原则——"声明式场景，命令式验证"**

```
// 好的契约 API（声明式）
const popoverContract = defineContract({
  name: 'IrisPopover',
  scenarios: [
    { given: 'closed', act: 'OPEN', expect: { open: true, ariaExpanded: true } },
    { given: 'open', act: 'ESC', expect: { open: false, onOpenChange: [false] } }
  ]
})

// 不好的契约 API（过度抽象）
const popoverContract = new ContractMachine(
  StateMachine.create({ ... })  // ❌ 不要用状态机描述契约——契约就是规范，不是实现
)
```

**原则 2：中间件设计——"pub/sub for state machines，不是 AOP"**

不要做成 AOP（面向切面编程）式的 before/after advice——那会与现有 controller 高度耦合。而是：

```
// ✅ 事件发射模式
resourceController.on('filter:change', ({ prev, next }) => { ... })

// ❌ AOP 模式
resourceController.beforeFilter((fn) => { ... })  // 过度耦合
```

**原则 3：Singleton API——"工厂函数，不是类"**

与整个 Iris UI 风格一致（`createSelectionModel`、`createExpansion` 都是工厂函数）：

```
// ✅
const safe = createSafeSingleton('key', () => new Map())

// ❌
class SafeSingleton { ... }  // 类不易 tree-shake
```

### 3.2 是否需要新的抽象层

**结论：需要两个新的抽象层。**

| 抽象层     | 包                       | 理由                                                         |
| ---------- | ------------------------ | ------------------------------------------------------------ |
| 契约定义层 | `@iris-ui/contracts`     | 当前无"行为规范"的显式存在；测试是隐式规范，但不可跨框架共享 |
| 可观测性层 | `@iris-ui/observability` | 位于 core 之上、devtools 之下；纯 core 不应引入可观测性字符  |

**不做**的新抽象层：

- **不要**做"跨框架运行时桥接层"——现有 4 个适配器已经是桥接，再加一层会导致"3 层抽象"（core → new layer → react/vue/...），过度工程。
- **不要**做"统一的测试框架"——Vitest + jsdom 已够用，契约场景在 vitest 中运行即可。

### 3.3 如何保持向后兼容性

**契约包**：零侵入。`defineContract` 只是定义，不注入任何运行时。适配器选择是否运行验证。

**可观测中间件**：可选参数。`createResourceController(options)` 中加 `{ middlewares?: Middleware[] }`，未传入时行为完全不变。

**Singleton 协议**：逐步迁移。先提供 `createSafeSingleton` 工厂，现有 singleton 逐步替换。不在同一 PR 中做全量替换。

**保真度门禁**：CI only。不影响任何包产物。

**突变测试**：CI only。不影响任何包产物。

## 4. 技术选型

### 4.1 是否需要引入新技术栈

| 方向           | 选型建议                | 理由                                                   |
| -------------- | ----------------------- | ------------------------------------------------------ |
| 契约运行       | **自建**（无依赖）      | 契约定义是一组普通 TS 类型 + 运行时 assert，不需要框架 |
| 可观测中间件   | **自建**（无依赖）      | middleware pipeline ~30 行核心代码                     |
| Singleton 安全 | **自建**                | `beforeEach`/`afterEach` + SSR 检测，标准 50 行        |
| 保真度测量     | **自建**（基于契约）    | 是契约运行结果的后处理 + diff                          |
| 突变测试       | **Stryker**（引入依赖） | 业界标准，不要自建突变引擎                             |

**Stryker 评估**：

| 维度     | 评估                                        |
| -------- | ------------------------------------------- |
| 成熟度   | 🟢 Stryker 已到 v8，社区活跃                |
| 框架支持 | 🟢 支持 Vitest 原生集成                     |
| 性能     | 🟡 慢（突变的本质），但可以通过增量模式缓解 |
| 维护负担 | 🟢 配置一次即可，CI pipeline 中运行         |

**不需要引入的新框架**：

- Playwright/Cypress（E2E）：当前 jsdom 测试已覆盖组件逻辑，E2E 是方向①⑨的范围外，不做）
- Storybook：VitePress 文档站 + playground 已够用
- Changesets：已使用，不需要换

### 4.2 第三方依赖评估标准

| 标准       | 权重 | 说明                                      |
| ---------- | ---- | ----------------------------------------- |
| 无框架依赖 | 最高 | 引入的依赖不能依赖 React/Vue/Solid/Svelte |
| 无副作用   | 高   | tree-shakable，不污染全局                 |
| 包体积     | 高   | core 10KB 预算敏感                        |
| 维护活跃   | 中   | 至少最近 1 年有更新                       |
| 许可       | 中   | MIT/Apache                                |

### 4.3 自建 vs 采购决策

| 功能     | 决策            | 理由                                                    |
| -------- | --------------- | ------------------------------------------------------- |
| 契约定义 | 自建            | 高度领域特定（UI 行为规范），太特定以至于现有工具不支持 |
| 中间件   | 自建            | 核心代码 30 行，不值得依赖                              |
| 突变测试 | 采购（Stryker） | 自建突变引擎是 10000+ 行的工作量，且 Stryker 已成熟     |
| SSR 单例 | 自建            | 核心代码 50 行，不值得依赖                              |

## 5. 实施路线图

### 5.1 优先级划分

```
P0（立即—不可绕过）
├── 方向③ Singleton SSR 安全协议    ← 已发现生产隐患（Svelte toast）
├── 方向① 运行时契约验证系统          ← 其他方向的基石（保真度/突变测试依赖它）

P1（下一阶段—质量体系完善）
├── 方向⑤ 突变测试质量放大            ← 依赖方向①的契约场景作为 oracle
├── 方向④ 跨框架行为保真度门禁        ← 依赖方向①的契约场景作为输入

P2（后续—开发者体验提升）
├── 方向② 数据管线可观测中间件        ← 价值明确但非阻塞
```

### 5.2 阶段划分

**Phase 1：基础建立（2-3 周）**

目标：Singleton SSR 安全 + 契约系统的 MVP

```
里程碑 M1（Week 1）
└── createSafeSingleton 实现
    ├── SSR 环境自动检测（typeof window）
    ├── 客户端返回真实实例
    ├── afterEach 自动 reset
    └── CI lint rule: no-raw-module-global

里程碑 M2（Week 2-3）
└── @iris-ui/contracts 包
    ├── defineContract / Scenario 类型定义
    ├── 首批 10 个核心契约场景（Popover/Dialog/Toast/Select/List/...）
    ├── 在 react 适配器中运行契约验证
    └── CI 步骤：契约场景通过率门禁
```

**Phase 2：质量体系（3-4 周）**

目标：突变测试 + 保真度门禁

```
里程碑 M3（Week 4-5）
└── 突变测试集成
    ├── Stryker 配置（core 包）
    ├── nightly pipeline
    ├── 阈值设定（初期 80% mutation score）
    └── 增量报告（哪些代码"杀不死"）

里程碑 M4（Week 6-7）
└── 跨框架保真度门禁
    ├── 首批契约场景扩展到 4 框架
    ├── 保真度计算器（状态/回调/DOM 三维度）
    ├── CI 步骤：四框架保真度 ≥ 99%
    └── 差异容忍机制（合法框架特性差异白名单）
```

**Phase 3：可观测性（2-3 周）**

目标：数据管线可观测

```
里程碑 M5（Week 8-10）
└── 可观测中间件
    ├── resourceController 中间件 pipeline
    ├── 事件发射（filter/sort/page/fetch 生命周期）
    ├── devtools 插件消费（playground 集成）
    └── 中文包友好（中间件事件名 i18n）
```

### 5.3 风险与缓解

| 风险                                              | 可能性 | 影响 | 缓解                                                       |
| ------------------------------------------------- | ------ | ---- | ---------------------------------------------------------- |
| 契约场景定义偏抽象，不覆盖真实 bug                | 高     | 中   | Phase 1 先写 10 个最常用的场景，验证效果后再扩展           |
| 突变测试过慢（core ~100 files）                   | 中     | 中   | 增量模式（只 mutate changed files）、nightly 而非每 commit |
| 保真度门禁产生大量 false positive（框架特性差异） | 高     | 高   | 建立"合法差异白名单"，初始保真度阈值设为 95% 而非 100%     |
| 事实核查发现的 Svelte toast bug 扩散              | 中     | 高   | Phase 1 立即先行修复已知 singleton 问题，不等到完整协议    |
| 中间件增加 resourceController 心智负担            | 低     | 中   | 中间件只在显式 opt-in 时激活，默认不开启                   |

**关键缓解策略：渐进式、非破坏性、增量交付。**

每一个 Phase 交付的都是可独立使用的价值：

- Phase 1 交付后：SSR 安全已有保障，10 个契约场景开始捕获回归
- Phase 2 交付后：测试质量已有量化数据，跨框架漂移可被 CI 捕住
- Phase 3 交付后：开发者可以 debug CRUD 数据流

**没有"必须全部完成才有价值"的巨量交付。** 这是原则。

## 总结：架构演进的关键决策

```
当前状态：
  core ──→ react/vue/solid/svelte
  └── 测试保障：~1500 测试全绿，但跨框架漂移无量化

演进后的状态：
  @iris-ui/contracts  ← 契约定义（行为规范，框架无关）
       │
  core ──→ react/vue/solid/svelte
   │            │
   │            └── 契约验证（各框架运行同一组场景）
   │
   ├── createSafeSingleton（SSR 安全）
   ├── resourceController + middleware（可观测）
   │
  CI 门禁：
    ├── 契约通过率（每个框架 ≥ 100%）
    ├── 保真度得分（四框架一致性 ≥ 99%）
    └── 突变测试（nightly, score ≥ 80%）
```

五个方向中，**方向①（契约）和方向③（SSR 安全）是架构基石**。方向①为方向④和⑤提供了"正确性 oracle"，方向③直接修复已发现的生产隐患。方向②是高价值但独立的价值增强。

**最关键的架构决策**：不要为这五个方向做"大统一"——不要做一个框架把契约、中间件、保真度、突变测试全部包装。每个方向是独立的包、独立的 CI 步骤、独立的演进节奏。它们可以协同，但**各不依赖**。
