## 发现 #3：setByPath / getByPath 中的原型污染

| 字段     | 值                                                                                                                                                                                                                                                                                                                                                                                     |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 类别     | 输入验证                                                                                                                                                                                                                                                                                                                                                                               |
| 严重性   | **高**                                                                                                                                                                                                                                                                                                                                                                                 |
| 标题     | `setByPath` 和 `getByPath` 不限制路径段 — `__proto__` / `constructor.prototype` 段可能导致原型污染                                                                                                                                                                                                                                                                                     |
| 位置     | `packages/core/src/path.ts` — `getByPath()`（第 56–64 行），`setByPath()`（第 73–85 行），`deleteByPath()`（第 88–103 行）                                                                                                                                                                                                                                                             |
| 描述     | 三个路径遍历函数直接从用户提供的路径字符串接受任意段。它们不阻止 `__proto__`、`prototype` 或 `constructor` 段。虽然表单引擎构造自己的路径（来自组件的 `name` 属性，而不是直接用户输入），但 `useField` / `useFieldArray` 钩子允许消费者传递任意路径字符串。如果消费者将不受信任的值向下传递到路径中，攻击者可以 `setByPath(formState, '__proto__.x', value)` 并污染 Object.prototype。 |
| 攻击场景 | 使用 `useFieldArray` 并允许用户通过 UI 添加/删除数组项的表单。如果任何人都可以将操作系统数据（例如 URL 查询参数）映射到字段名称，则路径 `constructor.prototype.hasOwnProperty = ()=>true` 可能绕过后续的 `hasOwnProperty` 检查。更可能：恶意 `IrisFormField` `name="__proto__.polluted"` props 向下传递到 `setFieldValue`。                                                            |
| 影响     | 原型污染 — 影响所有对象的属性查找。可能导致认证绕过、数据泄露或拒绝服务。                                                                                                                                                                                                                                                                                                              |
| 建议     | 在 `parsePath()` 或 `setByPath()` 中添加卫兵，拒绝路径段等于 `__proto__`、`prototype` 或 `constructor`。或者，使用 `Object.create(null)` 来保存表单值。在将路径写入 store 之前，通过验证 `Object.prototype` 未被修改来进行防御性检查。添加单元测试来证明路径 `"__proto__.malicious"` 被拒绝。                                                                                          |
| 工作量   | S（< 1 天）                                                                                                                                                                                                                                                                                                                                                                            |

| 描述     | 数据源架构是完全通用的 — 爬虫可以是任何返回数据的函数。这在安全方面是合理的（没有限制）。然而，common pattern 是消费者将 `fetch("/api/...")` 作为爬虫传递。如果用户输入控制爬虫 URL（例如，`createDataSource({ fetcher: (q) => fetch(userSuppliedUrl + q.page) })` ），则 SSRF 成为可能。这是消费者代码中的消费者风险。 |
| 攻击场景 | 一个使用 `createDataSource({ fetcher: (q) => fetch(`https://api.internal/${q.page}`) })`的 CMS 页面，如果用户控制`q.page`，则可能 fetch 内部服务。                                                                                                                                                                      |
| 影响     | 仅当消费者将用户输入合并到爬虫 URL 且未清理时。                                                                                                                                                                                                                                                                         |
| 建议     | 在 core data-source 的文档中添加明确的安全说明，列出 SSRF 预防。向 `DataSourceQuery` 添加一个 `requestInit?: RequestInit` 字段，以允许消费者安全地传递凭据。                                                                                                                                                            |
| 工作量   | S（< 1 天 — 文档）                                                                                                                                                                                                                                                                                                      |

| 类别           | 评估                                                                                                                                                                               |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **S** 冒充     | 低 — UI 使用 React 的声明式渲染；没有身份冒充原语。Toast 操作可能被欺骗调用赎金回调，但需要 XSS。                                                                                  |
| **T** 篡改     | **中等** — 发现 #3（原型污染）和发现 #2（公式注入）允许有意义的数据篡改。Markdown 清理器可以被绕过以注入 HTML。                                                                    |

## 最终总结

### 整体安全态势：需要改进 (Needs Improvement)

Iris UI 具有**良好的基础安全 hygiene** — 没有 `eval`，没有不安全使用 `innerHTML` 除了 markdown 插件（已记录危险），基础 CSP nonce 支持，正确使用 `textContent` 而非 `innerHTML` 进行皮肤引导，以及一个深思熟虑的不可变 store 架构，最小化基于类的攻击面。

然而，**三个严重发现**（Markdown XSS 清理不完整、CSV 公式注入、原型污染）需要在生产部署前解决。皮肤系统的持久化设计引入了通过 CSS 进行数据外泄的次要路径，但需要另一个漏洞来利用。

### 3 个最严重问题

| #   | 问题                           | 严重性 | CVSS v3 估计 | 原因                                                               |
| --- | ------------------------------ | ------ | ------------ | ------------------------------------------------------------------ |
| 1   | Markdown 清理绕过 → 存储型 XSS | 严重   | 8.8          | 基于正则的清理器无法抵御现代 XSS 向量。DOMPurify 是最小修复。      |
| 2   | CSV/Excel 公式注入             | 严重   | 8.6          | 在导出时未消毒的 `=`, `+`, `-`, `@` 前缀允许在打开时执行远程代码。 |
| 3   | setByPath 原型污染             | 高     | 7.5          | 任意路径段可能导致 Object.prototype 污染。                         |

### 前 3 名快速获胜

| #   | 胜利                                                     | 工作量 | 影响                             |
| --- | -------------------------------------------------------- | ------ | -------------------------------- |
| 1   | 在 `csvField()` / `cell()` 中添加公式前缀清理            | < 1 天 | 消除严重（CVSS 8.6）公式注入向量 |
| 2   | 在 `parsePath()` 中添加 `__proto__` / `constructor` 卫兵 | < 1 天 | 低工作量消灭原型污染（CVSS 7.5） |
| 3   | 在所有 4 个框架中为验证错误消息添加 XSS 合约测试         | < 1 天 | 确保证明未来回归的测试保护       |

### 安全债

- **Markdown 清理器**应从基于正则的清理升级为 `DOMPurify`。当前的正则流水线不能应用于所有 XSS 向量（SVG、MathML、CSS 表达式、HTML 实体编码、大小写变体、空字节注入）。估计工作量：1-3 天，包括测试。
- **Trusted Types** 兼容性：每个使用 `innerHTML`/`dangerouslySetInnerHTML` 的适配器需要一个 `TrustedHTML` 策略。随着浏览器强制执行，应提前添加以防止破坏。
- **皮肤持久化完整性**：当前的 `localStorage` 读取具有基于键的回退，但可以通过验证存储的 ID 进行加固。
- **合约测试套件**应扩展一个 XSS 测试合约场景，覆盖所有 4 个框架中所有基于文本的组件（Input、Textarea、TagInput、Mentions、Select、Table cells、Toast title/description）。
- **文档**应包含一个专门的安全页面，覆盖 CSRF、SSRF、CSP、CORS 和安全标头配置，针对每个部署目标（Vite、Next.js、Remix、Nuxt）。
