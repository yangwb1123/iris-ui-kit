## 1. 架构评估

### 1.1 当前架构的核心优势

| 维度              | 评估       | 证据                                                                    |
| ----------------- | ---------- | ----------------------------------------------------------------------- |
| **逻辑分离度**    | ⭐⭐⭐⭐⭐ | A/B/C 分类模型是业界最佳实践；core 零框架依赖已被 `grep` 严格验证       |
| **跨框架对齐**    | ⭐⭐⭐⭐⭐ | 四框架 149 组件同名同语义，contract 测试验证行为一致性                  |
| **插件契约**      | ⭐⭐⭐⭐   | `createPlugin`/`runPlugins` 接口清晰，注册式（非 monkey-patch）设计正确 |
| **主题/皮肤系统** | ⭐⭐⭐⭐⭐ | Token 杠杆 93% 节省已验证；皮肤继承/补丁/防 FOUC 设计成熟               |
| **质量基础设施**  | ⭐⭐⭐⭐   | 1500+ 测试 · 四道质量门 · size budget · axe 无障碍 · SSR 安全           |

**核心判断**：Iris UI 的架构**设计正确性**是一流的。A/B/C 下沉分类、core-first、薄桥适配器——这些原则在 4 框架 × 149 组件的规模上已被实证可行。少有的 monorepo 能同时管理 4 个反应式框架的等价行为并保持 core 零框架导入。

### 1.2 当前架构的关键局限性

但**设计正确 ≠ 执行完整**。交叉验证暴露了一个系统性的执行缺口：

```
分析产出：   136 份源文档 × 5 方向 = 680 方向-次论述
交叉验证：   138 份 .out.md 文件
实际采纳：   未追踪（无决策记录系统）
```

这是**元架构债务（Meta-Architectural Debt）**：分析系统产出远超决策系统的消化能力。每次新分析都声称"已读 65+ 已有分析"，但交叉验证发现每个新方向平均有 5-73 份前置覆盖——说明：

1. **分析之间没有引用链**——第 N+1 份分析不引用第 N 份，即使覆盖相同方向
2. **交叉验证发现的事实错误从不回流修正源分析**——方向三（AI 渲染优化）的 `useMemo` 计数错误（声称 2 处 vs 实际 35+ 处）在 .out.md 中指出，但源文档仍保留错误断言
3. **无"已决策/已分配/已拒绝/已排期"状态**——每个方向都以"高 ROI"、"P0/P1"结尾，但没有跟踪哪个建议被采纳

### 1.3 关键设计决策评估

| 决策                 | 合理性      | 执行缺口                                                                 |
| -------------------- | ----------- | ------------------------------------------------------------------------ |
| A 类逻辑下沉 core    | ✅ 正确     | ❌ Desktop OS 的 `planner.ts`/`remoteApp.ts`/`depth.ts` 四副本——直接违反 |
| 插件系统的注册式契约 | ✅ 正确     | ❌ 插件零错误处理（13 插件无 try/catch）                                 |
| 跨框架 contract 测试 | ✅ 正确     | ❌ 应用层（22 应用仅 6 冒烟测试）完全空白                                |
| Token-driven 渲染    | ✅ 正确     | ❌ 无运行时性能基准验证 93% 节省承诺                                     |
| CLI + MCP 双工具     | ✅ 战略正确 | ❌ `scaffoldSnippet` 两套独立实现                                        |

**模式**：所有设计决策在**原则层面**都是正确的，但**执行层面**存在系统性缺口。这不是架构设计错误，而是**架构治理缺失**——没有机制确保原则在应用层被贯彻。

### 1.4 架构债务全景

| 债务类型                        | 严重程度 | 影响面                | 修复成本                             |
| ------------------------------- | -------- | --------------------- | ------------------------------------ |
| 🟥 元架构债务（分析堆积无决策） | 高       | 工程效率 · 决策质量   | 中（建立决策记录系统）               |
| 🟧 Desktop OS 逻辑四副本        | 高       | 维护成本 · 行为对称性 | 低（下沉到 core，~1 天）             |
| 🟧 插件零错误处理               | 高       | 生产可靠性 · 生态信任 | 中（定义 PluginError 类型，~3 天）   |
| 🟧 应用层零测试                 | 高       | 重构安全 · CI 盲区    | 高（Playwright 框架 + 5-8 E2E 测试） |
| 🟨 性能基准缺失                 | 中       | 性能回归不可检测      | 中（5-8 bench 文件 + CI 棘轮）       |
| 🟨 CLI↔MCP 代码分裂             | 中       | 开发者体验不一致      | 低（提取 `@iris-ui/codegen`）        |
| 🟩 跨分析引用缺失               | 低       | 分析质量              | 低（分析模板强制引用已有分析 ID）    |

## 2. 扩展方向

基于交叉验证的结果，我筛选出 5 个**高价值且真正低覆盖**的扩展方向——其中 3 个来自已确认低覆盖度的分析，另外 2 个为元架构层面新提出。

### 方向 A：插件多实例化与作用域隔离架构（P1）

**来源**：`2026-07-11-architect-product-code-grounded-five-core-expansion-directions.md` 方向一  
**交叉验证覆盖度**：低（grep 确认最少已有论述）

| 维度               | 内容                                                                                                                                                                      |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **为什么需要**     | 当前 `PluginStoreMap` 是全局扁平 Map。两个 CodeMirror 编辑器同屏 → store 互相覆盖。这是 npm 发布后第一个会被社区报告的 bug                                                |
| **核心挑战**       | 全局注册（`registerTokens`/`registerMessages`）与实例级状态（`registerStore`）的边界划分；嵌套 Provider 的作用域链解析                                                    |
| **架构变更**       | ① `createScopedPlugin(name, scopeId)` 工厂 ② `IrisProvider` 增加 `scope` prop ③ `PluginRegistry` 分裂为全局注册表 + 实例注册表 ④ `usePluginStore(key, scopeId?)` 签名扩展 |
| **对现有系统影响** | 向后兼容：现有单例插件不传 `scope` → 行为不变。新增可选 `scope` 参数。核心变更集中在 `packages/core/src/plugin.ts`（~80 行）                                              |
| **技术价值**       | 填补架构的"实例化"能力——没有它，插件系统本质上是一个全局单例注册表，不是真正的实例化系统                                                                                  |

**设计选项**：

| 选项                                         | 方案                                                          | 权衡                                     |
| -------------------------------------------- | ------------------------------------------------------------- | ---------------------------------------- |
| **A** 作用域链式（类似 React Context 嵌套）  | `IrisProvider scope="a"` → 子 Provider scope="a/b"            | 灵活且熟悉，但 scope 解析复杂度 O(depth) |
| **B** 显式 ID（类似 Vue provide/inject key） | `IrisProvider scopeId={createScopeId()}`                      | 简单但无层级关系                         |
| **C** 命名空间前缀                           | `registerStore('editor', factory, { namespace: 'editor-1' })` | 最轻量，但命名空间管理靠约定而非强制     |

**推荐**：**A + B 混合**——默认作用域链（兼容嵌套场景），同时暴露 `createIsolatedScope()` 用于需要独立隔离的场景（微前端、SSR 多请求）。

### 方向 B：组件级能力与权限控制模型（P0）

**来源**：同上，方向二  
**交叉验证覆盖度**：低

| 维度               | 内容                                                                                                                                     |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **为什么需要**     | 企业采用的第一道问题："支持 RBAC 吗？" 当前答案"自己写"——对 UI 基础设施不可接受                                                          |
| **核心挑战**       | ① 复合表达式解析（`admin \|\| (editor && !auditor)`）② 服务端+客户端双重强制 ③ 异步能力解析 ④ 插件可注册自定义能力                       |
| **架构变更**       | 新增 `@iris-ui/core/capability` 子路径：`CapabilityContext` + `useCapability` hook + `IrisCapabilityProvider` + 组件级 `capability` prop |
| **对现有系统影响** | 纯增量，零破坏。组件新增可选 `capability` prop，不传入时行为不变                                                                         |
| **产品价值**       | 企业 PoC 的第一道门槛从"你们得自己写权限"变成"声明 `capability` prop 即可"                                                               |

**关键设计决策**：能力**模型** vs 能力**实现**的分离。

```
@iris-ui/core/capability  → 定义接口和 Context（模型）
│
├─ @iris-ui/capability-rbac    → 内置 RBAC 实现（角色→权限映射）
├─ plugin-capability-casbin    → Casbin 策略引擎集成（插件）
└─ plugin-capability-oauth     → OAuth Scope 映射（插件）
```

> **决定**：core 层只定义 `{ check: (capability: string) => boolean | Promise<boolean> }` 索引签名，不实现任何策略。策略由独立包或插件提供。这遵循了 Iris 的"core 保持精简，重型能力走插件"原则。

### 方向 C：组件状态记忆与视觉上下文恢复协议（P1）

**来源**：同上，方向四  
**交叉验证覆盖度**：低–中

| 维度               | 内容                                                                                                                 |
| ------------------ | -------------------------------------------------------------------------------------------------------------------- |
| **为什么需要**     | "刷新后回到第 5 页"是 SPA 用户对"专业应用"的基线期望。当前所有控制器状态纯内存，刷新即丢失                           |
| **核心挑战**       | ① 恢复优先级链（URL > session > default）② 过期数据 ③ 多标签页冲突 ④ 超大状态序列化性能                              |
| **架构变更**       | 新增 `StateMemoryStorage` 接口 + `createStateMemory` 工厂 + 控制器可选 `memory` 参数。~120 行协议定义 + 各控制器接入 |
| **对现有系统影响** | 纯增量。`createPagination(config)` 新增可选 `{ memory: 'user-list' }`。不传入则行为不变                              |
| **复用路径**       | Desktop OS 的 `ProfileStorage` 已验证 `{ save, load }` 契约。提取为通用接口后所有控制器可复用                        |

**存储后端选项**：

| 后端              | 场景                   | 注意                            |
| ----------------- | ---------------------- | ------------------------------- |
| `sessionStorage`  | 默认——标签页生命周期   | 跨标签页不共享                  |
| `localStorage`    | 跨会话记忆             | 多标签页冲突（需 `tabId` 后缀） |
| `URLSearchParams` | 可分享状态             | 长度限制 ~8KB                   |
| `IndexedDB`       | 超大状态（200 行选择） | 异步读取可能产生闪烁            |
| 自定义（插件）    | 服务端持久化           | 需 `async save/load`            |

**推荐**：分层策略——`sessionStorage` 默认，URL 同步覆盖关键状态（页码、搜索词），`localStorage` 记录用户偏好（列宽、排序），插件可注册自定义 backend。

### 方向 E（架构治理）：跨框架构建工具链统一评估（P2）

**新提出**——同样未被 136 份分析覆盖。

| 维度               | 内容                                                                                                                               |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| **为什么需要**     | 当前构建是异构三工具链：tsup 数组配置（core/react/vue + solid 各一段）+ svelte-package。每次新增框架适配器都需配置新的构建管道     |

| 代码分割    | ✅           | ✅                     | ✅            | ❓       |
| DTS 生成    | ✅           | ✅                     | ⚠️            | ❓       |

## 3. 接口设计建议

### 3.1 五条接口设计原则

基于 Iris UI 的现状和 136 份分析的教训，我提炼以下接口原则：

| #   | 原则                      | 说明                                              | 当前违反示例                         |
| --- | ------------------------- | ------------------------------------------------- | ------------------------------------ |
| 1   | **增量入口，零破坏出口**  | 每个新能力必须是可选参数/可选导入，现有代码不修改 | `stateMemory` 可选参数 ✅            |
| 2   | **框架无关的契约在 core** | 接口定义、类型、默认实现在 `@iris-ui/core`        | `capability` 协议应在 core ✅        |
| 3   | **单层抽象，不套壳**      | 不创造"绑定之上的绑定"——core 接口直接用           | CLI↔MCP 的 `scaffoldSnippet` 重复 ❌ |
| 4   | **默认安全，opt-in 风险** | 安全/错误处理的默认行为是防御性的                 | 插件 `registerTokens` 无 sanitize ❌ |
| 5   | **决策驱动接口**          | 先写 ADR 再写接口，不是先写接口再改 ADR           | 136 份分析无决策记录 ❌              |

### 3.2 关键模块接口设计建议

#### 3.2.1 插件多实例化

```typescript
// @iris-ui/core/plugin

// 全局注册（不变）
interface PluginRegistry {
  registerTokens(tokens: Record<string, string>): void
  registerMessages(locale: string, msgs: Record<string, string>): void
  registerStore(key: string, factory: () => unknown): void // 全局单例
}

// 新增：实例化注册
interface ScopedPluginRegistry extends PluginRegistry {
  // 新增 scope 感知的重载
  registerScopedStore(key: string, factory: (scopeId: string) => unknown): void // 每 scope 独立实例
}

// IrisProvider
interface IrisProviderProps {
  plugins?: Plugin[]
  scope?: string // 新增可选
}
```

> **设计决策**：不改变现有接口签名。`registerStore` 仍注册全局单例（向后兼容）。新增 `registerScopedStore` 接收 `scopeId` 参数工厂。`usePluginStore` 新增可选 `scopeId` 参数，缺失时从 `IrisProvider` context 继承。

#### 3.2.2 组件级能力控制

```typescript
// @iris-ui/core/capability

// 核心接口（最小化）
interface CapabilityContext {
  check(capability: string): boolean | Promise<boolean>
  onCapabilityChange?: (handler: (cap: string) => void) => void
}

// 组件级 prop（可选）
interface CapabilityProps {
  capability?: string | string[] // 单能力 or 多能力（与关系）
  fallback?: ReactNode // 不满足时渲染的内容（默认 `null` → 隐藏）
}
```

> **设计决策**：`fallback` prop 而非 `mode="hidden|disabled|readonly"`——让消费者决定不满足能力时的展示策略，而不是组件系统预设。同时保持 prop 数量最少（1 个 `capability` + 1 个 `fallback`）。

#### 3.2.3 状态记忆协议

```typescript
// @iris-ui/core/state-memory

interface StateMemoryStorage {
  save(key: string, state: unknown, options?: { ttl?: number }): void
  load(key: string): unknown | null
  clear(key?: string): void
}

// 控制器集成（以 Pagination 为例）
interface PaginationConfig {
  page?: number
  pageSize?: number
  total?: number
  memory?: string // 可选 memory key，提供则自动 save/load
}
```

> **设计决策**：`memory` 是字符串 key（非对象配置）——保持 prop 扁平、可序列化、可与 URL 参数共用同一 key。存储后端通过全局 `setStateMemoryStorage()` 注入，默认 `sessionStorage`。

### 3.3 不需要引入的新抽象层

| 曾被提出      | 判断      | 理由                                                                                       |
| ------------- | --------- | ------------------------------------------------------------------------------------------ |
| 事件总线      | ❌ 不需要 | `createStore` + `subscribe` 已覆盖 95% 场景；插件间通信用 `registerStore` 共享状态而非事件 |
| Boot Protocol | ❌ 不需要 | `IrisProvider` + `runPlugins` 已是 boot 协议                                               |
| 微前端框架    | ❌ 不需要 | 超出 Iris UI 范围；与现有 `remoteApp.ts` 的模式正交                                        |
| 工作流引擎    | ❌ 不需要 | 超出范围；可在应用层通过 `createMachine` 组合                                              |

需要的新抽象只有一个：**ADR 决策记录**（非代码，是治理流程）。

## 4. 技术选型

### 4.1 不需要引入新的技术栈

136 份分析中反复出现"需要引入 X"的建议（RxJS、XState、Zustand、React Query、Playwright、Vitest Bench...）。我的评估：

| 建议引入     | 当前替代                  | 判断        | 理由                                                                        |
| ------------ | ------------------------- | ----------- | --------------------------------------------------------------------------- |
| RxJS         | `createStore` + `derived` | ❌          | core 的 store 模式已经足够；引入 RxJS 会破坏 "core 零依赖"                  |
| XState       | `createMachine`           | ❌          | Iris 的 `createMachine` 是定制化的 XState 子集，解决的是"太厚"的问题        |
| React Query  | `createAsyncResource`     | ❌          | core 已有 AsyncResource，需要的是"被插件使用"而非"替换"                     |
| Playwright   | Vitest + jsdom → 应用测试 | ✅ **推荐** | 应用层 E2E 测试只能用 Playwright/Cypress；Vitest + jsdom 模拟不了真实浏览器 |
| Vitest Bench | `scale.bench.ts`          | ✅ **推荐** | 已有 bench infra（vitest bench），只需扩展场景数量                          |

### 4.2 第三方依赖评估标准

鉴于 Iris UI 的"core 零框架依赖"原则，我对**任何新第三方依赖**使用以下五道门：

```
Gate 1: 能否在 core 中用 50 行纯 JS 实现？
        → 能 → 不引入依赖，手写
        → 不能 → Gate 2

Gate 2: 该依赖是否会被多个框架适配器共享？
        → 是 → 放在 core（作为 peer dep 或 optional dep）
        → 否 → 放在具体适配器的 dev deps

Gate 3: 该依赖是否需要在 SSR 环境中工作？
        → 是 → 必须支持 ESM + CJS + 无浏览器 API 静态引用
        → 否 → Gate 4

Gate 4: 该依赖的包大小（min+gzip）是否 > 5KB？
        → 是 → 必须做成独立子路径（如 `@iris-ui/core/feature-x`）
        → 否 → 可直接依赖

Gate 5: 该依赖是否有原生 ES module 输出？（非 UMD/CJS only）
        → 是 → 可接受
        → 否 → 拒绝（tree-shaking 不可用）
```

**当前库中通过/不通过的例子**：

| 依赖                 | Gate 1           | Gate 2        | Gate 3      | Gate 4   | Gate 5 | 结论                                     |
| -------------------- | ---------------- | ------------- | ----------- | -------- | ------ | ---------------------------------------- |
| `@floating-ui/dom`   | ❌ 浮层定位复杂  | ✅ 四框架共用 | ✅          | ❌ ~12KB | ✅     | ⚠️ 可接受，但应 lazy import              |
| `codemirror`（插件） | ❌ 编辑器引擎    | ✅ 插件       | ❌ 仅客户端 | ❌ 大型  | ✅     | ✅ 插件层可接受                          |
| `date-fns`（core）   | ❌ 日期解析复杂  | ✅            | ✅          | ⚠️ ~3KB  | ✅     | ⚠️ 建议 minis 子路径                     |
| `immer`（core）      | ⚠️ 50 行实现不了 | —             | —           | —        | —      | ❌ `createStore` 的 `produce` 回调已覆盖 |

### 4.3 自建 vs 采购决策

| 能力              | 自建                        | 采购（第三方）                       | 决策                                                                          |
| ----------------- | --------------------------- | ------------------------------------ | ----------------------------------------------------------------------------- |
| **状态记忆存储**  | ✅ 50 行接口 + 3 个内置实现 | `redux-persist`/`zustand/middleware` | **自建**——接口极简，第三方引入会破坏 core 零依赖                              |
| **能力控制引擎**  | ✅ 接口 + 默认 RBAC         | `casbin`/`casl`                      | **自建核心 + 插件集成**——core 只定义 `CapabilityContext`，casbin 集成做成插件 |
| **E2E 测试框架**  | ❌ 不可行                   | Playwright/Cypress                   | **采购**——不发明测试框架                                                      |
| **构建工具链**    | tsup 配置抽象               | Nx/Turborepo 远程缓存                | **已有 Turborepo**——只需共享 preset 配置，不引入新工具                        |
| **分析→决策系统** | 无代码——Markdown 文件       | Notion/Jira/Linear                   | **自建**——`docs/decisions/` + ADR 模板，不引入外部系统                        |

## 总结

### 对交叉验证的回应

交叉验证文档的结论是正确的：**5 个方向均已被已有分析覆盖**。但这不意味着这些方向不重要——恰恰相反，它们被多份独立分析反复发现，说明它们是**跨多个分析者视角的共同结论**，可信度高于"某一份分析发现的方向"。

### 真正未触及的问题

136 份分析覆盖了几乎所有的"功能方向"（插件、状态、表单、测试、性能...），但**没有一个分析覆盖"如何从分析切换到执行"**。这是最大的架构盲区——不是技术架构，而是决策架构。

### 架构师的核心建议

> **停止写第 137 份分析。从今天开始写第一份 ADR。**

Iris UI 的架构设计质量是一流的。它不缺"发现"——缺的是"决定"。建立 ADR 决策记录系统，将 136 份分析归档，把已验证的方向转为决策，然后开始执行。这是从"组件库"进化到"应用框架"之前的最后一道门槛——不是技术门槛，是工程治理门槛。
