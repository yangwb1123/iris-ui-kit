# 架构分析报告：Iris UI 系统评估与扩展方向

## 1. 架构评估

### 1.1 当前架构的核心优势

Iris UI 的架构核心假设——「逻辑下沉 core，适配器做薄桥」——已通过 4 框架 × 149 组件对齐得到实践验证。这是一条**已被证明正确**的架构路径，不应质疑基础假设。

**优势总结：**

| 维度           | 优势                                       | 架构价值                                                               |
| -------------- | ------------------------------------------ | ---------------------------------------------------------------------- |
| **分层纯度**   | Layer 0–4 的切分 + A/B/C 下沉分类法        | 每一层职责单一，跨层耦合仅通过 token/css 变量 + store 接口，无隐式依赖 |
| **测试对称性** | 2646 行 contract 测试 × 4 框架             | 行为正确性可在 core 层一次验证，框架层仅验证桥接正确性                 |
| **Token 杠杆** | 30 tokens vs 800 行裸 CSS                  | 系统级换肤 = 修改变量，非修改组件                                      |
| **插件契约**   | `createPlugin` + `usePluginStore` 非侵入式 | 重型能力不进 core，保持 core 在 10KB 预算内                            |
| **AI 原生**    | manifest + llms.txt + MCP 服务器           | 开发者体验与 AI 辅助开发的前瞻性布局                                   |

### 1.2 架构债务与技术债

**显性债务（已确认）：**

1. **a11y 覆盖率债务（严重）**
   - 149 组件中仅 ~16（11%）被 axe 覆盖
   - 124+ 重型组件（Tree/Table/Calendar/Cascader/ColorPicker/Transfer/Tour/Splitter）为零覆盖
   - 这不是测试遗漏，而是**合规风险**：任一组件的不合规 aria 模式可导致产品层面违反 WCAG 标准
   - 技术债性质：非重构债，而是测试基建缺失债——修复方式不是「改代码」而是「加测试」

2. **视觉回归测试真空（严重）**
   - 零截图/像素对比测试 × 149 组件 × 4 框架 × 2 主题 = **1192 视觉组合**
   - 每周 CSS 变更 + 皮肤系统的 token patch 能力 = 视觉退化可无声通过所有现有质量门
   - 当前质量门的验证盲区：（行为测试 ✅）→（a11y 扫描 ⚠️ 部分）→（视觉回归 ❌）

3. **CSS Token 全局泄漏**
   - 所有 `var(--iris-*)` 写入 `:root`，无 ShadowRoot/`@scope` 隔离
   - 微前端/嵌入场景：两个 Iris UI 实例 → token 命名冲突 → 样式污染
   - 骨架系统（`namespace`）存在但是存储级的，非 CSS 命名空间级的

**隐性债务（潜在但未确认）：**

4. **框架桥接层性能未测量**
   - `core/src/scale.bench.ts` 仅测纯 JS 逻辑
   - 无基准证明「适配器是薄桥」——这是核心架构主张但缺乏数据验证
   - 风险：若某框架桥接层有未发现的性能瓶颈（例如 Svelte 5 runes 的 `$state` 滥用导致的重复渲染），架构层面的「薄桥」主张可能局部失效

5. **MCP 基础设施的演进方向未固化**
   - 当前 manifest → MCP → AI 代码生成的管线已在运转
   - 但 manifest 数据同时可以服务于编译时类型生成、文档生成、契约测试生成——**这组下游消费者缺乏统一的类型契约**
   - 风险：每个新的 manifest 消费者都自己解析 JSON 并推断类型，导致隐式耦合

### 1.3 关键设计决策的合理性评估

| 决策                                   | 状态    | 评述                         |
| -------------------------------------- | ------- | ---------------------------- |
| Core 零框架依赖                        | ✅ 正确 | 已验证通过 4 框架对齐        |
| Token 驱动换肤                         | ✅ 正确 | 30:1 的杠杆率证实了设计动机  |
| 状态机只用于有事件语义的组件           | ✅ 正确 | 已建立防 svjs 退化的判别准则 |
| 插件系统不做 `registerComponent`       | ✅ 正确 | 保留类型安全和 tree-shaking  |
| Contract 测试跨框架复用                | ✅ 正确 | 2646 行 × 4 的高复用比       |
| `pnpm gen:manifest` 从 barrel 自动生成 | ✅ 正确 | 保持「手不维护组件清单」原则 |

**一个值得重新审视的决策：**

> **CSS 命名空间与皮肤 namespace 的分离**

当前设计：皮肤 `namespace` 仅作用于存储键（localStorage key），不影响 CSS 变量名。这意味着：

- 两个 Iris UI 实例即使使用不同皮肤，它们的 CSS 变量名完全相同（都是 `--iris-primary`）
- 隔离只能通过 Shadow DOM 实现，但当前零 ShadowRoot

这是一个在设计初期合理的简化决策（因为嵌入/微前端不是 MVP），但**现在需要决定命名空间策略**——是延续「仅存储隔离」还是扩展到「CSS 变量名隔离」（如 `--iris-embedded-primary`）。这个决策影响方向四的全部实现路径。

## 2. 扩展方向

以下 5 个方向按优先级排序，每个方向从前述评估文档的分析结论出发，延伸到架构设计层面。

### 方向 A：渲染协议质量层（合并原方向① + ③）

**优先级：P0 — 立即启动**

#### 为什么需要

当前的质量体系有一个结构性缺口：

```
行为正确性（contract tests）→ ✅ 2646 行
a11y 合规性（axe）         → ⚠️ 11% 覆盖
视觉一致性（screenshot）   → ❌ 0 覆盖
```

这个缺口不是三个独立任务的简单组合——它们是同一个问题的三个剖面：「组件在真实浏览器中渲染后，如何保证其正确性？」

**业务价值：**

- 合规风险：WCAG 违规可能导致产品在法律层面不可用
- 品牌风险：视觉退化可无声通过 CI，直到上线被发现
- 维护成本：缺少视觉回归意味着 CSS 重构只能靠人工审查

**技术价值：**

- 统一的渲染测试编排框架 = 降低三套基础设施的维护成本
- Manifest 驱动的测试矩阵生成 = 新增组件自动获得三套测试

#### 核心挑战

**挑战 1：渲染环境的基础设施选择**

这里需要做一个关键决策——在真实浏览器（Playwright）还是 jsdom 中跑 a11y 和视觉测试？

| 选项                             | ax 兼容性 | 截图能力    | 速度           | CI 集成        |
| -------------------------------- | --------- | ----------- | -------------- | -------------- |
| Playwright + axe-playwright      | ✅ 原生   | ✅ 原生截图 | 慢（~3s/组件） | 需浏览器二进制 |
| jsdom + axe-core                 | ✅ 可行   | ❌ 无       | 快             | 无额外依赖     |
| Playwright + jest-image-snapshot | ✅        | ✅          | 慢             | 需浏览器二进制 |

对于视觉测试，Playwright 是唯一可行选项。a11y 测试在 jsdom 中可运行但会丢失渲染后 aria 状态（浮层组件的 open 状态无法通过 jsdom 触发）。

**建议方案：** 采用 **Playwright 单引擎**，统一承载 a11y + 视觉 + 行为合约。虽然速度慢于 jsdom，但避免了双环测试的同步头。

**挑战 2：1192 视觉组合的管理策略**

149 × 4 × 2 = 1192 不是一次性截图的数字——首次运行全部截图会产生 1200+ 基准图，CI 耗时和存储都是问题。

**策略选项：**

| 策略                        | 优点      | 缺点                          |
| --------------------------- | --------- | ----------------------------- |
| 全量首次 + 增量维护         | CI 全覆盖 | 首次 ~40+ min；1200+ 截图入库 |
| 仅 diff 敏感组件            | 速度快    | 可能漏掉不预期的视觉变化      |
| Manifest 标记 + 按版本 diff | 渐进式    | 需要新的 manifest 字段        |

**建议：** 采用**三级策略**——P0 组件（高风险/高频变更：Table/Tree/Dialog/Popover/Form 等约 20 组件 × 4 × 2 = 160 图）优先；P1 组件（约 60 组件 × ...）；P2 组件（剩余）。通过 `manifest.json` 新增 `"visualTestingPriority": "P0"|"P1"|"P2"` 字段控制。

#### 预期的架构变更

1. **新增包**：`packages/test-renderer/`——测试渲染编排层，不依赖任何单一测试框架
2. **Manifest 扩展**：新增 `visualTestingPriority`、`a11yAllowlist`（框架特定的 axe 违规白名单）
3. **合约场景扩展**：`ContractScenario` 新增 `screenshot?: true` 标记 + `openRequired?: boolean` 标记浮层组件
4. **CI 新增**：`pnpm turbo run test:render` —— Playwright 并行执行

#### 对现有系统的影响

- **正面**：合约测试无需改动，渲染测试是加法
- **风险**：Playwright 的 CI 二进制缓存需要纳入 `pnpm setup`；~40min 的全量运行可能需要分片
- **向后兼容**：完全兼容，现有测试不动

### 方向 B：编译时类型代码生成管线

**优先级：P1 — 方向 A 之后启动**

#### 为什么需要

当前 Manifest（`manifest.json`）的数据质量——每个组件的 props 含 name/type/optional/default/enum/description——已足以支撑编译时类型生成。但当前仅被 MCP 消费用于运行时代码生成，未被用于 TypeScript 编译时类型生成。

```mermaid
当前：barrel → manifest.json → MCP → AI 代码生成
期望：barrel → manifest.json → MCP → AI 代码生成
                            ↘  types.generated.ts → 编译时类型检查
```

**业务价值：**

- 框架适配器类型与 manifest 的「单一事实源」统一
- 插件 `registerStore('key', factory)` → `usePluginStore<'key'>()` 的类型安全
- i18n key 的枚举类型（`t('table.loading')` → 编译时报错若 key 不存在）

**技术价值：**

- 消除手动类型声明与 manifest 数据之间的隐式耦合
- 为 AI 代码生成提供更结构化的类型输入（而非自然语言 prop 描述）

#### 核心挑战

**挑战 1：运行时注册 vs 编译时提取的矛盾**

`registerStore('key', factory)` 是运行时调用，TypeScript 无法在编译时推断 `key` 的类型。类型生成需要静态扫描——类似 `gen:manifest` 的 barrel 扫描。但插件包的 registerStore 调用分散在各框架适配器中，没有统一的入口扫描路径。

**解决思路：**

- 在插件包中约定一个**声明式注册文件**（如 `plugin-registrations.ts`），`gen:types` 扫描该文件而非分散的 install 函数
- 代价：增加了一个」插件作者必须写声明文件「的约束

**挑战 2：i18n key 的聚合来源**

`t('table.loading')` 的 key 来自两个来源：

- core 的默认英文字典（`packages/core/src/i18n/en.ts`）
- 插件的 `registerMessages` 调用

类型生成需要扫描两者。这要求 `gen:types` 理解 `registerMessages` 的调用模式，而非简单的 JSON 文件读取。

#### 预期的架构变更

1. **新增脚本**：`scripts/gen-types/`——独立于 `pnpm gen:manifest`，因为产出物不同
2. **新增产物**：`packages/*/src/types.generated.ts`——可由 gitignore 管理，但需 `prepublish` hook 确保存在
3. **插件注册声明**：新增 `packages/plugin-*/plugin-registrations.ts` 约定

#### 对现有系统的影响

- **正面**：类型安全是纯加法，不破坏现有运行时
- **风险**：`gen:types` 需要与 `gen:manifest` 保持同步（二者解析同一套 barrel），否则会漂移
- **缓解措施**：CI 中加一步 `pnpm gen:types && git diff --exit-code` 确保一致性

### 方向 C：CSS Token 命名空间与嵌入协议

**优先级：P2 — 方向 A/B 之后**

#### 为什么需要

当前所有 `var(--iris-*)` 写入 `:root`，在以下场景构成问题：

1. **微前端集成**：两个独立部署的 Iris UI 应用在同一个页面中 → token 命名冲突
2. **CMS 嵌入**：AdminLayout 嵌入到已有系统 → token 覆盖宿主样式
3. **皮肤市场**：用户同时安装多个皮肤包 → token 覆盖导致视觉不可预测

**业务价值：**

- 嵌入场景是 CMS 应用的核心功能需求
- 微前端架构是中型以上项目的常见选择

**技术价值：**

- 解决了 token 系统在组合场景下的「非设计内」使用

#### 核心挑战

**挑战 1：协议设计——应用级 vs 作用域级**

需要回答一个关键设计问题：命名空间是应用配置（`<IrisProvider namespace="embedded">`）还是 CSS 作用域机制（`@scope` / Shadow DOM）？

| 选项                                  | 实现复杂度       | 隔离强度               | 与皮肤系统的集成               |
| ------------------------------------- | ---------------- | ---------------------- | ------------------------------ |
| CSS 变量名前缀（`--iris-embedded-*`） | 中               | 中（仍存在于同一 DOM） | 需修改 `applyCssVars`          |
| `@scope`                              | 低（浏览器原生） | 高                     | 需 polyfill（Safari 支持有限） |
| Shadow DOM + `attachShadow`           | 高               | 最强                   | 需重构组件渲染层次             |
| CSS 命名空间 + `contain`              | 中               | 中                     | 需额外 containment 配置        |

**建议方案：** 采用 **CSS 变量名前缀**方案，原因：

- 与现有皮肤系统的 `namespace` 骨架语义一致（当前仅存存储，扩展为 CSS 变量名）
- 不引入 Shadow DOM 的隔离开销（slot 传递、事件重定向、样式穿透）
- `@scope` 作为未来演进方向（当浏览器支持成熟时）
- 不需要重构组件渲染层次

**挑战 2：与 SkinProvider 的集成**

当前 `applyCssVars` 写入 `document.documentElement.style`。启用 namespace 后：

```
// 当前
applyCssVars(theme) → :root 上的 style.setProperty('--iris-primary', ...)

// 启用后
applyCssVars(theme, { namespace: 'embedded' })
  → IrisProvider 容器的 style.setProperty('--iris-embedded-primary', ...)
```

这个转换是**函数签名级别的变更**——所有调用 `applyCssVars` 的地方都需要检查是否需要 namespace。风险在于现有调用点忘记更新不会编译报错，只会导致 namespace 不生效。

#### 预期的架构变更

1. **修改**：`applyCssVars` / `applyTheme` 函数新增 `options: { namespace?: string, target?: HTMLElement }` 参数
2. **修改**：`SkinProvider` / `IrisProvider` 在应用 token 时传递 namespace
3. **新增工具函数**：`toNamespacedCssVarName(name: string, namespace: string): string` → `--iris-primary` → `--iris-embedded-primary`
4. **文档新增**：嵌入场景的使用指南和最佳实践

#### 对现有系统的影响

- **正面**：零组件级改动，仅影响主题/皮肤基础工具函数
- **风险**：现有 `applyCssVars` 调用点的兼容性（全部需要检查是否应该透传 namespace）
- **向后兼容**：函数签名添加可选参数，完全向后兼容

### 方向 D：框架桥接层性能基准系统

**优先级：P2 — 方向 A/B 之后，与 C 并行**

#### 为什么需要

当前架构核心主张是「适配器做薄桥」，但有**零个数据**支持这个主张。这不是说主张错误，而是缺少「可验证的架构健康度指标」：

```
现有数据：❌ 无跨框架渲染基准
           ❌ 无适配器层性能断言（"thin bridge" 的定量定义缺失）
           ✅ core 纯 JS 基准（scale.bench.ts）
```

**业务价值：**

- 在选择框架时，性能数据是客观决策依据
- 避免某框架桥接层退化导致用户感知性能下降

**技术价值：**

- 将「薄桥」从架构主张变为可验证的约束
- 如果某框架桥接层超出预算（例如每次渲染多执行了 2 倍调配逻辑），CI 可告警

#### 核心挑战

**挑战 1：基准的定义——什么是「薄桥」？**

需要定义「薄桥」的操作化指标。建议三个维度：

| 指标               | 定义                                                   | 预算  | 测量方法      |
| ------------------ | ------------------------------------------------------ | ----- | ------------- |
| 渲染开销比         | `(框架适配器渲染时间 - core 逻辑时间) / core 逻辑时间` | < 20% | 微基准测量    |
| 框架桥接代码行数比 | `(适配器代码行数 / core 控制器代码行数)`               | < 30% | 静态分析      |
| 冗余渲染次数       | 一次 state 变更触发的框架渲染次数                      | ≤ 1   | 框架 profiler |

**核心难点在于第一个指标**：如何只测量「适配器渲染时间」而不包含 core 逻辑？如果 adapter 的 render 函数调用了 core 的 `getValue()`，测出的时间是两者之和。需要通过**打桩**将 core 逻辑替换为 mock 来隔离变量。

**挑战 2：跨框架的公平比较**

React 的 `mount` → `useSyncExternalStore` → `setState` 路径与 Svelte 5 的 `$state` 响应式路径无法在「毫秒」维度直接对比——React 的 reconciliation 与 Svelte 的编译时更新机制本质不同。比较「4 框架谁更快」是错误的目标。

**正确的比较：同框架内「有桥接 vs 无桥接」的自比**。

- 对一个框架，测：原生组件（直接 DOM 操作） vs Iris 组件（通过桥接）
- 用「桥接引入的开销比例」作为跨框架对比的归一化指标

#### 预期的架构变更

1. **新增包**：`benches/framework-bridge/`——不是生产包，是基准设施
2. **新增夹具**：四个框架的「裸渲染」基准组件（`NativeButton` vs `IrisButton`）
3. **新增 CI Job**：`pnpm turbo run bench:bridge`——在 CI 中定期运行，非 blocking（不阻塞 PR 合并，仅预警）
4. **新增文档**：`FRAMEWORK_BRIDGE_BENCHMARKS.md`——记录基线值

#### 对现有系统的影响

- **正面**：零影响，新增测试设施仅用于验证
- **风险**：基准需要稳定的环境（CI 机器的性能波动可能导致告警噪音）
- **缓解措施**：记录运行 10 次的中位数而非单次值；允许 ±20% 的波动范围

### 方向 E：插件声明的静态分析框架

**优先级：P2 — 方向 B 的前置依赖**

#### 为什么需要

插件系统当前的注册是纯运行的——`createPlugin({ install(reg) { reg.registerStore(...); reg.registerMessages(...) } })`。这种设计对运行时友好，但对编译时分析不透明：

- 无法静态枚举所有已注册的 store key
- 无法静态提取 i18n message key 集合
- 无法在编译时验证 `usePluginStore('non-existent-key')` 的类型安全

这与方向 B（类型代码生成）形成依赖链——**没有静态插件声明分析，类型生成只能覆盖 core 组件，无法覆盖插件扩展的类型**。

#### 核心挑战

**挑战 1：声明式注册的约定设计**

需要在「不破坏插件运行时 API」的前提下，添加静态分析入口。核心问题是：静态声明文件是**强制**还是**可选**？

| 选项                             | 优点         | 缺点                                         | 建议                             |
| -------------------------------- | ------------ | -------------------------------------------- | -------------------------------- |
| 强制声明文件（每个插件必写）     | 分析确定性强 | 双文件维护成本                               | 适合重型插件（pro-table/editor） |
| 自动从 install 函数 AST 提取     | 零额外负担   | 精度受限（`registerStore` 的参数可以是变量） | 适合轻量插件（locale-zh）        |
| 混合：声明文件可选，AST 分析兜底 | 灵活性最大   | 两套实现，复杂度高                           | 不推荐                           |

**建议方案：** 强制声明文件（`plugin-registrations.ts`），原因：

- 插件数量预期有限（首批 3 个），增加一个文件的成本可控
- AST 分析的精度问题会导致不可预测的类型行为——类型安全领域容不得「可能正确」
- 声明文件同时可作为插件的 API 参考文档

**挑战 2：声明文件的格式**

声明文件需要能够表达：

```ts
// plugin-registrations.ts
export const registrations = {
  stores: [
    {
      key: 'editor-state',
      type: EditorState, // 携带类型信息
    },
  ],
  messages: {
    'zh-CN': {
      'editor.save': '保存',
      'editor.cancel': '取消',
    },
  },
  tokens: {
    '--iris-editor-bg': '...',
  },
} as const // <-- 关键：const assertion 保留类型
```

`as const` 是关键——没有它，`key: 'editor-state'` 的类型是 `string` 而非 literal type，类型生成工具无法提取具体 key 名称。

#### 对现有系统的影响

- **正面**：新增文件而非修改现有文件；现有插件仍可工作（声明文件是纯加法）
- **风险**：插件作者可能忘记维护声明文件 → 类型生成不完整
- **缓解措施**：`gen:types` 扫描到插件但没有声明文件时 **warning 而非 error**；CI 中检测声明文件缺失

## 3. 接口设计建议

### 3.1 关键原则

根据前述分析，以下接口设计原则适用于所有新增/修改的架构层：

| 原则             | 含义                                   | 应用场景                                |
| ---------------- | -------------------------------------- | --------------------------------------- |
| **增量非破坏**   | 新增接口不得修改现有接口的语义或签名   | 所有方向                                |
| **可选即解耦**   | 可选参数是默认的向后兼容方式           | `applyCssVars` 的 namespace/target 参数 |
| **合同即测试**   | 新接口必须有对应的 contract 或渲染测试 | 方向 A 的核心设计                       |
| **声明多于命令** | 接口偏声明式，注册式优于命令式调用     | 方向 E 的插件声明文件                   |
| **框架无感知**   | 新接口不应该引用任何框架 API           | Core 函数的 namespace 参数与框架无关    |

### 3.2 是否需要新的抽象层

**需要引入的抽象层：**

1. **渲染测试编排器**（方向 A）
   - 位置：`packages/test-renderer/`（新包）
   - 职责：将 manifest + scenario → 可执行的 Playwright 测试矩阵
   - 接口设计：
     ```
     renderTestMatrix(manifest, {
       frameworks: ['react', 'vue', 'solid', 'svelte'],
       components: ['IrisButton', 'IrisTable'],  // 可选：仅特定组件
       tests: ['contract', 'a11y', 'visual'],     // 可选：仅特定测试类型
       visualPriority: ['P0', 'P1', 'P2']         // 可选：仅特定优先级
     })
     ```
   - 设计理由：将测试生成逻辑从具体的测试框架（Vitest/Jest/Playwright）中抽象出来，确保测试编排器与测试运行框架解耦

2. **类型代码生成器**（方向 B + E）
   - 位置：`scripts/gen-types/`（新脚本包）
   - 职责：将 manifest + 插件声明 → `types.generated.ts`
   - 接口设计：
     ```
     generateTypes({
       manifest: ManifestJson,
       pluginRegistrations: PluginRegistration[],
       output: 'packages/*/src/types.generated.ts'
     })
     ```
   - 设计理由：与 `gen:manifest` 解耦，因为两个生成器的触发频率不同（manifest 在组件变更时，types 在插件或 API 变更时）

**不需要引入的抽象层：**

- 不需要「公共 CSS 隔离层」——token 命名空间直接在 `applyCssVars` 级别实现，不需要额外的 CSS 层抽象
- 不需要「统一性能基准框架」——每个框架的基准可以独立运行，不需要统一的基准运行器

### 3.3 向后兼容性策略

| 变更                    | 策略                                   | 证据                           |
| ----------------------- | -------------------------------------- | ------------------------------ |
| `applyCssVars` 新增参数 | 可选参数，缺省行为 = 当前行为          | 现有调用点无需修改             |
| Manifest 新增字段       | 添加字段，`undefined` 表示无配置       | 现有消费端（MCP）忽略未知字段  |
| 插件声明文件            | 新增文件，现有插件无需添加             | `gen:types` 扫描缺失时 warning |
| 渲染测试编排器          | 新增包，不修改现有测试                 | 现有 Contract 测试独立运行     |
| A11y 白名单配置         | Manifest 新增字段，不改变现有 axe 调用 | 白名单在无配置时 = 空数组      |

## 4. 技术选型

### 4.1 是否需要引入新技术

| 方向                | 技术选择                                                                      | 影响评估                           |
| ------------------- | ----------------------------------------------------------------------------- | ---------------------------------- |
| 方向 A（渲染测试）  | **Playwright**（已存在吗？检查依赖）                                          | 新增 ~40MB 浏览器二进制，CI 需配置 |
| 方向 A（视觉 diff） | `@playwright/test` 的 `expect().toMatchScreenshot()` 或 `jest-image-snapshot` | 前者与 Playwright 集成更紧         |
| 方向 B（类型生成）  | TypeScript 编译器 API（`ts-morph`）                                           | 纯 JS 依赖，无额外二进制           |
| 方向 C（CSS 隔离）  | 无需新技术，仅函数变更                                                        | 纯 JS 变更                         |
| 方向 D（基准）      | `vitest/benchmark`                                                            | 已存在依赖                         |
| 方向 E（静态分析）  | `ts-morph` 或 `ts-json-schema-generator`                                      | 纯 JS 依赖                         |

**决策点：Playwright 的浏览器管理**

目前 `package.json` 无 Playwright 依赖。引入 Playwright 需要决定：

| 选项                                                                | CI 复杂度            | 开发者体验 | 建议                                                         |
| ------------------------------------------------------------------- | -------------------- | ---------- | ------------------------------------------------------------ |
| Playwright 全量（chromium + firefox + webkit）                      | 高（~150MB 缓存）    | 全         | **不推荐**——CI 时间 + 存储成本过高                           |
| Playwright 仅 chromium                                              | 中（~40MB 缓存）     | 够用       | **推荐**——chromium 覆盖 90%+ 场景，firefox/webkit 可后续扩展 |
| Playwright + `@playwright/experimental-ct-(react/vue/solid/svelte)` | 高（四框架 CT 配置） | 最佳       | 不推荐——Component Testing API 在四个框架间的兼容性不一致     |

**最终建议：** Playwright 仅 chromium + 在独立的 CI job 中按组件分片并行。

### 4.2 第三方依赖评估标准

新增依赖的评估清单：

1. **必要性**：能否用已有依赖实现？→ 能则不自引
2. **大小**：本身 + 传递依赖的大小 → core 的 10KB 预算不适用于测试设施（无包大小限制）
3. **维护活跃度**：GitHub 最近 6 个月的提交/发布频率
4. **框架绑定**：是否限制于特定框架？→ 必须框架无关（方向 A 的编排器）
5. **SSR 安全**：是否依赖浏览器 API？→ 测试设施不要求 SSR 安全

**预期新增依赖清单：**

| 依赖               | 用途                  | 框架绑定 | 大小  | 理由                               |
| ------------------ | --------------------- | -------- | ----- | ---------------------------------- |
| `@playwright/test` | 渲染测试编排          | 否       | ~40MB | 唯一可行选项                       |
| `axe-playwright`   | Playwright + axe 集成 | 否       | 轻量  | 替代方案：手动注入 axe-core        |
| `ts-morph`         | 类型代码生成          | 否       | ~8MB  | 替代方案：手写字符串处理（不推荐） |
| `@changesets/...`  | 已存在                | —        | —     | 无需新增                           |

### 4.3 自建 vs 采购

| 能力           | 选项                    | 建议       | 理由                                                                                                  |
| -------------- | ----------------------- | ---------- | ----------------------------------------------------------------------------------------------------- |
| 渲染测试编排   | 自建                    | **自建**   | 需要与现有 manifest + contract 测试深度集成，通用 Playwright 配置生成器无法满足                       |
| 视觉 diff 服务 | 采购（Chromatic/Percy） | **不推荐** | Chromatic 与 Storybook 强绑定（Iris 无 Storybook）；Percy 是 SaaS 费用；自建 `toMatchScreenshot` 足够 |
| 类型生成       | 自建                    | **自建**   | 需要理解 Iris 的 barrel 解析逻辑 + 插件声明格式，通用工具（如 `json-schema-to-typescript`）无法处理   |

**自建 vs 采购的架构决策依据：**

对于渲染测试编排器，有一个「为什么不直接复用 Playwright 的 Component Testing？」的决策需要做。

Playwright CT 的优点是官方维护，支持四框架的 Component Testing API。但有以下不匹配：

- Iris 的 Contract 测试不在组件挂载点做断言，而是在 store/controller 状态上做断言
- Playwright CT 的定位是「组件单元测试」，而 Iris 需要的是「跨组件的行为验证」+
- Iris 已经有 2646 行 Contract 测试，迁移到 Playwright CT 意味着全部重写

**结论：自建渲染测试编排器，它不替代 Contract 测试，而是在 Contract 测试之上叠加 a11y + 视觉。**

### 5.3 长期架构健康度指标

对于每个扩展方向，建议建立持续性指标来验证架构健康度：

| 指标                 | 测量方式                                   | 当前值     | 目标值      | 检查频率 |
| -------------------- | ------------------------------------------ | ---------- | ----------- | -------- |
| **A11y 覆盖率**      | `(axe 测试组件数) / (总组件数)`            | 11%        | 95%+        | 每次 PR  |
| **视觉回归通过率**   | `(通过截图数) / (总截图数)`                | N/A        | 99.5%+      | 每次 PR  |
| **类型覆盖率**       | `(typed props) / (总 props)`               | MCP 运行时 | 100% 编译时 | 每周     |
| **桥接开销比**       | `(适配器渲染时间 - core 时间) / core 时间` | N/A        | < 20%       | 每周 CI  |
| **Token 隔离完整性** | ShadowRoot / @scope / namespace 使用组件数 | 0          | 按需        | 里程碑级 |

### 5.4 不做事项（明确排除）

1. **Storybook 集成**：与 Iris 的「合约测试优先」原则不一致——Storybook `play()` 功能虽然可以做行为测试，但与现有的 2646 行 Contract 测试重叠，不提供增量价值
2. **Puppeteer 替代 Playwright**：Playwright 的 axe 集成（`axe-playwright`）和跨浏览器支持优于 Puppeteer
3. **CSS-in-JS 方案**：当前 token + CSS 变量方案已有 30:1 的杠杆率，CSS-in-JS 不会提供额外杠杆，反而增加运行时开销
4. **端到端测试**：`test-renderer` 定位在组件级渲染测试，不是用户流程级别的 E2E（E2E 属于应用层的范畴）
5. **性能预算仪表盘**：当前规模（4 框架 × 149 组件）下，性能预算更适合作为 CI 门禁，而非需要仪表盘可视化

## 总结

Iris UI 当前架构核心——**core 逻辑 + 薄桥 + token 驱动**——已被实践验证为正确。评估文档识别的 5 个方向覆盖了 a11y、DX、视觉、隔离和性能五大领域，方向判断准确。我的分析在以下三个维度上有补充：

1. **优先级重排**：将视觉回归从 P2 上调至 P0（与 a11y 合并为「渲染协议质量层」），因为 1192 视觉组合 + 零覆盖的隐性回归风险被低估
2. **技术挑战细化**：a11y 方向的实际成本从 ~5 天修正为 ~8 天（跨框架 aria 模式差异治理）；类型生成的插件声明静态分析作为前置依赖被单独识别（方向 E）
3. **实施策略**：将 5 个方向重组为 3 个阶段、8 周交付周期，核心思想是『渲染质量先行，类型和嵌入跟进』

最终建议：**从渲染协议质量层开始**——这堵住了当前质量体系中唯一的漏洞（视觉退化可无声通过），并同时提升 a11y 覆盖率，为后续方向建立可信的测试基础设施。
