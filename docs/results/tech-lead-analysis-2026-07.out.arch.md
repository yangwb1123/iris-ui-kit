# Iris UI 架构分析：验证报告基础上的架构评估与扩展路线

## 架构评估

### 核心架构优点

Iris UI 的架构设计在理念上是业界领先的——其 **A/B/C 下沉分类模型**（核心身份/附加/纯材料）提供了一个清晰的心智模型，指导每个逻辑片段应该放在哪里。实际执行也令人印象深刻：

- **Core 与框架的严格隔离**已兑现——`packages/core/src` 中无框架导入（AGENTS.md 铁律 #1 已验证）
- **四条薄桥模式**工作正常：`createStore` → `useSyncExternalStore` / `ref` / `createSignal` / `$state` 映射一致且经过良好测试
- **合同系统**（39 场景 × 4 框架 = 156 测试路径）是确保四框架行为对等性的独特工程资产——很少有 UI 库能在这一层面实现可验证的跨框架对等性
- **插件契约**（`createPlugin`/`runPlugins`）设计得当——加法式、无组件注册、拓扑排序依赖关系
- **Token 杠杆**已兑现（~30 token vs 800 行裸 HTML/CSS），皮肤继承机制（`extends` + 自定义命名空间）为市场做法的上层建筑提供了良好的基础

### 架构债务与技术债

通过代码库验证和验证报告交叉引用，我识别出以下结构性问题：

| 类别           | 债务项                                                                                                                | 严重程度 | 修复成本                                   |
| -------------- | --------------------------------------------------------------------------------------------------------------------- | -------- | ------------------------------------------ |
| **接口债务**   | 三个表单子模块（`createValidationEngine`、`createStepNavigation`、`createFieldValueOps`）已实现但未从公共 barrel 导出 | 高       | 低（~5 行 barrel 导出 + 1 个 PR）          |
| **验证债务**   | `contract-coverage.test.ts` 仅检查场景**名称是否存在于测试文件中**——不检查测试是否通过或断言是否具有辨别力            | 高       | 低（增加名称 → 结果断言映射）              |
| **监控债务**   | 插件注册**无运行时验证**——组件在未注册时静默降级，无开发者警告                                                        | 中       | 低（~10 行守卫 + 插件注册表）              |
| **工具链债务** | 12 个插件的构建配置（`tsup.config.ts`）高度重复——只有 `external` 数组和 Solid 的 esbuild 插件不同                     | 中       | 中（共享构建预设，每个插件 ~5 行配置）     |
| **验证债务**   | ESLint 插件仅包含 3 条规则——缺少 `require-contract-attr`、`no-framework-antipattern`、`enforce-barrel-export`         | 中       | 低（每条规则 ~30-50 行）                   |
| **架构债务**   | 桌面 OS 应用视图在 4 个框架中重复业务逻辑（计算器、终端、照片、文件）——违背了核心下沉原则                             | 中       | 高（每个应用都需要提取 + 重构）            |
| **测试债务**   | SSR 对等性无统一验证——4 个 SSR 应用（Next/Nuxt/SolidStart/SvelteKit）各自独立测试                                     | 中       | 高（每个框架需要框架特定的 runner 适配器） |
| **文档债务**   | `createValidationEngine`/`createStepNavigation` 的 API 表面已实现但在框架适配器的 `useForm` hook 中不可用             | 中       | 低（每个适配器增加方法转发）               |

### 关键设计决策是否合理

**A/B/C 分类**：合理且执行得当。一个值得注意的观察是，该模型目前在两个类别之间的**中间地带**最弱——即部分提取的场景（如表单 step API 已就绪但未公开暴露，桌面 OS 应用视图有核心服务但业务逻辑仍重复）。这不是模型本身的问题，而是其应用的完成度问题。

**插件契约**：设计合理。`registerStore`/`registerLazyStore`/`registerTokens`/`registerMessages`/`onTeardown` 是正交的，涵盖了连接 UI 库所需的全部内容。不包含 `registerComponent` 的决策是正确的——避免了运行时类型擦除和摇树优化问题。

**合同系统**：其最优雅的设计选择是让合同场景成为**纯数据**（`Scenario` 对象），而非字节码或 DSL。这使得它们可组合、可静态分析且可测试。Runner/driver 分离是同类中最好的。但是，该系统的实际**验证深度**被夸大了——合同仅测试 DOM 属性对等性，不测试行为正确性或边界条件。

**形态机准则**：`createMachine` 仅用于有真实状态转换的组件（`OPEN`/`CLOSE`/`TOGGLE`）的决策是防止过度工程的正确应急措施。在 149 个组件中，该约束得到了很好的遵守。

## 高价值架构扩展方向

### 方向 1：插件注册运行时验证（P0）

**为什么需要**：目前，`usePluginStore('key')` 在插件未注册时静默返回 `undefined`，导致后续解构时出现难以调试的运行时崩溃（`Cannot read properties of undefined`）。这是一个开发者体验问题——错误信息无法帮助用户理解*为什么* store 不可用。

**核心挑战**：

1. 守卫必须兼容生产环境的死代码消除（不增加包体积）
2. 需要区分"插件已注册但 store 不存在"和"插件根本未注册"
3. 必须支持 HMR 和动态插件切换（`reloadPlugins`）

**架构变更**：

- 在 `runPlugins` 的 `CollectedRegistrations` 中增加 `registeredPluginNames: Set<string>`
- `usePluginStore` 需要接收 `name` 参数（标识哪个插件拥有该 store）
- 开发守卫：`process.env.NODE_ENV !== 'production'` 时，在 `usePluginStore` 中检查插件是否已注册

**对现有系统的影响**：极小。向后兼容（生产构建中通过死代码消除移除守卫）。`createPlugin` 不需要变更。这是"小投入大产出"的典型案例。

### 方向 2：合同覆盖执行深度化（P0→P1）

**为什么需要**：当前 `contract-coverage.test.ts` 仅检查场景名称的存在性——它不检查（a）场景是否实际通过，（b）断言是否具有辨别力，或（c）被审计组件集是否随时间增长。这意味着一个场景如果有三个断言且全部失败，只要它出现在适配器测试文件中，覆盖检查仍然通过。

**核心挑战**：

1. 需要区分"名称存在"和"测试通过"——理想情况下，读取 vitest 的 JUnit XML 输出或模拟套件结果
2. 断言密度守卫（`assertion-density.test.ts`）确保每一步至少有一个断言，但未检查该断言是否验证了*有意义的*状态——创建"虚假断言"（`expect(true).toBe(true)`）太容易了
3. 覆盖系统需要*增长强制*——目前没有机制确保组件覆盖率随代码库增长而提高

**架构变更**：

- 合同覆盖守卫需要新的抽象层：**合同验证器**，它运行合同并为每个适配器收集通过/失败/跳过结果
- `manifest` 包应生成覆盖报告，对比"合同覆盖组件"与"barrel 组件"
- 新的质量门：`pnpm check:contract-fullness`，当覆盖率低于基线时使 CI 失败

**权衡**：

- **方案 A（推荐）**：增强现有 `contract-coverage.test.ts`，从 `ContractScenario` 定义中读取预期组件覆盖率目标，交叉引用 manifest 的组件计数。最具成本效益的改进。
- **方案 B**：构建完整的合同结果聚合器。与其他方案相比更正确但投资回报率更低。

### 方向 3：统一插件构建预设（P1）

**为什么需要**：所有 12 个插件包都重复几乎相同的 `tsup.config.ts` 模式——唯一的变量是入口、外部依赖，以及 Solid 是否使用 `esbuild-plugin-solid`。这意味着：

- 添加新插件需要从现有插件复制 ~30 行配置
- 构建配置中的 bug 必须修补 12 次
- 任何构建工具的变更都需要 12 次更新

**核心挑战**：

1. Svelte 需要独特的处理（`svelte-package` 打包 + 单独的 `svelte.config.js`）
2. Solid 需要 `esbuild-plugin-solid` Babel 插件
3. 每个插件有不同的外部依赖数组（CodeMirror vs 图表库 vs 无）
4. 构建配置必须是可组合的，以便插件可以"选择"其需求

**架构变更**：

- 新的包：`@iris-ui/build-preset` 或工具包根目录的 `packages/build/`
- 导出 `definePluginConfig(base, options)` 用于：
  - `framework: 'solid'` → 应用 Solid esbuild 插件
  - `external: string[]` → 追加到默认 Iris 外部依赖
  - `entries: Record<string, string>` → 入口映射
  - `svelte: true` → 返回 svelte-package 配置（单独传递给 turbo）
- 每个插件的 `tsup.config.ts` → 5 行

**对现有系统的影响**：纯重构。所有构建产物在功能上应相同。此更改需要与构建流水线协调，以处理 Svelte 的独特打包器。

### 方向 4：SSR 对等性骨架（P2）

**为什么需要**：目前，4 个 SSR 应用（`apps/ssr-next`、`ssr-nuxt`、`ssr-solidstart`、`ssr-sveltekit`）各自独立运行其测试。无法确保一个框架中修复的 SSR bug 在其他框架中得到防范。鉴于 Iris 的 token 驱动渲染严重依赖 CSS 变量注入——这在 SSR 上下文中容易被破坏——这是一个真实的风险。

**核心挑战**：

1. 每个框架的 SSR 运行时完全不同（Next.js 的 `renderToString` vs Nuxt 的 `useHead` vs SolidStart 的流式传输 vs SvelteKit 的构建时渲染）
2. 没有通用的 SSR 测试 runner——合同系统的 driver 模式不能轻易推广到 `node` 环境（不支持 jsdom 的 DOM API 子集）
3. SSR 故障通常发生在集成层面（不匹配、水合错误），而集成测试很难自动化

**架构变更**：

- `@iris-ui/core/ssr` 子路径，包含：
  - `SSRScenario` 数据，类似 `ContractScenario` 但用于 SSR 输出断言
  - 每个框架的 driver，包装其特定的 SSR API
- `manifest` 包中的 `ssr-coverage.test.ts` 守卫，强制执行所有核心组件至少有一个 SSR 合同

**权衡**：

- **方案 A（推荐）**：从小处着手——创建一个共享的 SSR 测试套件，仅覆盖顶级 token 注入、`IrisProvider` 包装和 5-10 个核心组件。可跨 4 个 SSR 框架运行，验证 IrisProvider 包装 + token 注入 + 基本组件渲染。设定基线，然后逐步扩展。
- **方案 B**：完整的 SSR-for-every-component 套件。过于雄心勃勃——按组件计算的成本效益太低。
- **方案 C**：跳过 SSR 统一验证，依赖每个框架的独立测试。成本最低但有风险。

### 方向 5：Core 表单 API 完成度（P1→P2）

**为什么需要**：验证报告正确地识别出 `createValidationEngine`、`createStepNavigation` 和 `createFieldValueOps` 已实现但未从公共 barrel 导出。这是一个架构接口债务——接口已定义，实现已完成，但消费者无法从框架层到达它们。此外，框架适配器的 `useForm` hook 不公开 step 导航方法，因此多步骤表单（wizard）虽然在 core 引擎中受支持，但在任何框架中都不可用。

**核心挑战**：

1. `createStepNavigation` 需要框架适配器的 `useForm` 公开 step 方法——每个适配器需要 3-5 行桥接代码
2. 多步骤表单的文档需要更新以匹配新的 API 表面
3. 表单引擎的 step API 目前只能通过 `createFormStore` 内部使用——如果外部消费，`FormStore` 类型需要调整

**架构变更**：

- barrel 导出：在 `core/form.ts` 和 `core/index.ts` 中增加 3 行 re-export
- 适配器桥接：每个适配器的 `useForm` hook 中增加 step 方法转发
- 类型导出：确认 `FormStep`、`FieldErrors` 已正确包含在公共类型中

**对现有系统的影响**：非常小。纯加法变更——无向后兼容性问题。

## 接口设计建议

### 关键模块的接口设计原则

1. **Core 子路径应遵循统一的注册模式**：当前，`@iris-ui/core` 的子路径（`/window`、`/fs`、`/profile` 等）以不同的模式导出——有些使用 `create*` 工厂，有些导出纯函数，有些导出对 store 的订阅。应建立统一契约：
   - 每个子路径应导出一个工厂（`create*`），该工厂返回一个 POJO 可订阅 store
   - 纯函数（如 `snapRect`、`compareValues`）应位于 `@iris-ui/core` 的根目录，而不是特定于应用的子路径

2. **表单引擎的 API 表面应与框架适配器对称**：`createFormStore`、`createValidationEngine`、`createStepNavigation` 和 `createFieldValueOps` 应作为 `@iris-ui/core/form` 下的独立导出提供。每个框架的 `useForm` 不应重新实现或包装这些工厂——它应仅仅将它们连接到反应性系统。

3. **合同场景应版本化**：当前，`ContractScenario` 是纯数据，但无法版本化。当合同场景发生变化时（添加或删除步骤），我们无法判断哪些适配器测试已更新。契约类型应包含一个 `version: number`，由适配器必须匹配的 runner 强制执行。

### 是否需要引入新的抽象层

**是：共享构建预设（`@iris-ui/build-preset`）**。当前的模式（每个包复制 `tsup.config.ts`）不具可扩展性。新增抽象层是合理的，因为它是：

- 纯构建时（无运行时成本）
- 可测试（预设是普通函数，接受配置并返回 `Options[]`）
- 可选的（包可以覆盖预设的默认值）

**否：统一 SSR 测试 runner（目前）**。为 SSR 测试创建一个抽象的 runner 层是诱人的，但 4 个 SSR 框架之间的差异太大，无法以合理的成本进行抽象。最好采用*共享场景数据 + 框架特定 runner* 的模式——这正式化了 Next/Nuxt/SolidStart/SvelteKit 当前在 `apps/ssr-*/test` 中各自为战的现状。

**有条件的：插件注册表抽象**。如果插件数量增长到 25+，应引入 `PluginRegistry` 的集中式开发监控层（`reg.getStoreUsage('editor')`、`reg.warnOnMissing('editorStore')`）。在此之前，15 个插件的规模不需要抽象。

### 向后兼容性

建议的更改大部分是加法，因此兼容性影响应最小化：

| 变更                | 向后兼容                    | 迁移路径                                                     |
| ------------------- | --------------------------- | ------------------------------------------------------------ |
| 表单 barrel 导出    | ✅ 纯加法                   | 无                                                           |
| 插件注册守卫        | ✅ 开发时，可死代码消除     | 无                                                           |
| 构建预设            | ✅ 重构，产物不变           | 需要更改 `tsup.config.ts` 的语法，但无需更改构建产物         |
| 合同版本化          | ⚠️ 需要版本检查             | 适配器 test runner 需要更新以通过版本号；旧场景版本视为 `v0` |
| SSR 骨架            | ✅ 纯加法，与现有测试并行   | 无                                                           |
| `useForm` step 方法 | ✅ 纯加法，现有表单不受影响 | 无                                                           |

## 技术选型

### 是否需要引入新的技术栈

**不引入新的框架或运行时时**。当前的技术栈（pnpm 9、Turborepo 2、tsup、Vitest、ESLint 9、Prettier 3）是合适的。缺失的工具能力需求可以通过扩展现有工具或添加轻量级库来满足：

| 需求             | 建议方案                                                                                   | 理由                                                               |
| ---------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| 构建配置组合     | 当前 `tsup` + `defu` 或简单的对象合并                                                      | 避免引入完整构建框架（如 unbuild）的开销；当前技术栈的功能已经足够 |
| 深度合同覆盖分析 | 增强 `contract-coverage.test.ts`，可选解析 vitest 的 JSON 输出（`vitest --reporter=json`） | 无新依赖                                                           |
| ESLint 规则扩展  | 继续使用 ESLint 9 flat config + `@types/eslint`                                            | 现有技术栈，扩展意味着编写规则                                     |
| 插件注册表监控   | 在 core 中使用 `Map<string, Set<string>>`，零依赖                                          | 无需新技术                                                         |
| 表单文档生成     | 使用 TypeScript 的 `ts-expose-internals` 或 `api-extractor`                                | 如果手动维护 barrel，则不需要；通过 barrel 导出强制完成            |

**关于代码生成**：代码库使用 `pnpm gen:manifest` 进行 manifest 生成。构建预设也应考虑类似的代码生成方法——不是运行时预设，而是生成 `tsup.config.ts` 文件的 `pnpm gen:build-config`。这将完全避免构建时抽象，同时保留 DRY 配置。

### 第三方依赖评估标准

对于任何新的依赖：

1. **SSR 兼容**：必须在 `node` 环境和浏览器中都能工作（不要使用 `window`、`document` 或无守卫的 `process`）
2. **树摇优化**：必须支持 ESM 死代码消除（理想情况下发布为 `"sideEffects": false`）
3. **体积预算**：gzip 后 < 5KB（对于共享工具依赖）或 < 1KB（对于单个包中的开发时使用）
4. **类型化**：必须提供 TypeScript 类型（如果声明文件不可用，则检查是否存在 `@types/*`）
5. **活跃维护**：最近的提交在 6 个月内，没有未解决的安全问题

### 自建 vs 采购的决策依据

| 能力         | 自建 | 采购 | 决策                                                      | 理由                                                                                                                                                     |
| ------------ | ---- | ---- | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 构建预设     | ✅   | ❌   | **自建**                                                  | 构建配置高度特定于 Iris 的 monorepo + 多框架打包器模式。通用的构建预设（如 `unbuild`）不处理 Solid 的 esbuild 插件 + Svelte 的 svelte-package 双轨模式。 |
| 插件注册守卫 | ✅   | ❌   | **自建**                                                  | <10 行代码。不值得外部依赖。                                                                                                                             |
| 合同深度验证 | ⚠️   | ⚠️   | **自建**                                                  | 可能使用现有的 `vitest` 报告格式，但逻辑特定于 Iris 的合同架构。外部合同测试框架不存在（原因相同——每个 UI 库都有自己的行为定义）。                       |
| 表单文档生成 | ⚠️   | ✅   | **采购（api-extractor/ts-docs）**                         | 有多种成熟的文档生成器。Iris 不应重新发明 `tsdoc` 解析。如果手动维护文档结构，可以跳过。                                                                 |
| SSR 渲染测试 | ❌   | ✅   | **采购（现有 vitest/jsdom + 各框架自己的 SSR 测试工具）** | 不要为 SSR 测试构建统一的运行时。使用每个框架的现有方法（Next 的 `next-test-utils`、Nuxt 的 `@nuxt/test-utils` 等）。Iris 应仅提供*场景数据*。           |

## 实施路线图

### 优先级排序（P0/P1/P2/P3）

```
P0（立即——2 周内）
├── 插件注册运行时验证       # ~4 行核心代码 + 1 ESLint 规则
├── 表单 barrel 完成度        # ~5 行导出 + 每个适配器 ~3 行
└── contract-coverage 深度化   # ~20 行增强 + 组件覆盖率基线

P1（短期——1-2 月）
├── 统一构建预设              # 共享包 + 12 个配置迁移
├── ESLint 规则扩展            # 3-4 条新规则
```

### 阶段划分和里程碑

**阶段 1：安全加固（P0，第 1-2 周）**

- 目标：消除静默失败模式 + 合同盲区
- 交付物：
  - 插件注册守卫 + 开发模式 ESLint 警告
  - 3 个表单子模块公开从 barrel 导出
  - contract-coverage 深度检查（场景名称 + 适配器矩阵 + 组件覆盖率基线）
  - 测试：所有现有测试必须保持绿色（无破坏性变更声明）

**阶段 2：工具链统一（P1，第 3-6 周）**

- 目标：降低构建配置重复性并执行架构规则
- 交付物：
  - `@iris-ui/build-preset` 或等效的共享配置
  - 4 条新的 ESLint 规则：`require-contract-attr`、`no-framework-antipattern`、`enforce-barrel-export`、`no-core-framework-import`
  - 所有 12 个插件迁移到新构建预设
  - 测试：产物的 diff 检查，确保构建输出与预迁移相同

**阶段 3：表单完成度（P1→P2，第 4-8 周）**

- 目标：使表单引擎的全部功能从框架层可达
- 交付物：
  - 每个适配器的 `useForm` hook 公开 step 导航（`nextStep`、`prevStep`、`goToStep`）
  - `createFieldValueOps` 可用于独立使用（用于 `useFieldArray` 场景）
  - 多步骤表单的文档（VitePress + code 示例）
  - 测试：覆盖多步骤导航、数组字段操作和验证引擎独立使用的合同场景

**阶段 4：SSR 和桌面 OS 提取（P2，第 9-16 周）**

- 目标：涵盖两个最大的架构债务项
- 交付物：
  - SSR 场景数据 + 一个框架（Next.js）的 SSR 集成测试
  - Calculator 应用视图提取到 `@iris-ui/core`（Proof-of-concept）
  - Terminal 命令处理提取到 `@iris-ui/core`
  - 每个提取应用的框架适配器桥接（每个 ~20-30 行）
  - 测试：提取的逻辑的单元测试 + 跨框架合同场景

### 风险点和缓解策略

| 风险                                   | 概率 | 影响       | 缓解策略                                                                                                                       |
| -------------------------------------- | ---- | ---------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **构建预设破坏 Svelte 构建**           | 中   | 高         | 逐步迁移插件（一次一个），为 Svelte 插件保留独立的 `svelte.config.js`。在合并前对每个迁移的插件运行完整的构建。                |
| **ESLint 规则产生误报**                | 高   | 中         | 使用 `'warn'` 级别而非 `'error'` 发布新规则。在 CI 中运行错误报告以收集误报，然后提升严重级别。                                |
| **表单 step API 暴露增加维护负担**     | 低   | 低         | 该 API 已在 core 中实现——暴露它不需要新的维护。适配器桥接是简单的转发。                                                        |
| **SSR 测试骨架过于雄心勃勃**           | 中   | 中         | 从小处着手（单个框架，核心组件子集）。如果投资回报率被证明为负，可选择放弃。SSR 场景数据在没有测试 runner 的情况下仍然有价值。 |
| **合同覆盖深度化发现真正的跨框架 bug** | 高   | 中（正面） | 这实际上是期望的结果。清理时，将 bug 修复作为单独的 PR 提交，保留合同增强。                                                    |
| **桌面 OS 应用视图提取发现跨框架假设** | 中   | 中         | 一些应用视图（如 Notepad）每个框架使用不同的文本编辑器实现。提取应限于纯逻辑（撤销栈、保存定时器）；保持渲染框架特定。         |

### 执行建议

1. **并行处理 P0**：插件守卫 + 表单 barrel + 合同深度化可以并行工作——它们接触不同的文件，没有共享依赖
2. **构建预设作为阶段 2 的依赖**：在扩展 ESLint 规则之前，先统一构建配置，因为某些规则（如 `enforce-barrel-export`）可能在未重构的构建配置上产生误报
3. **在阶段 1 和阶段 2 之间留出一个缓冲周**：用于处理因合同覆盖深度化而暴露的任何跨框架 bug
4. **将桌面 OS 提取与产品节奏解耦**：它是一个架构清理，而非面向用户的功能——不将其与任何发布日期绑定
5. **为新包建立容量规划**：@iris-ui/build-preset 如果与官方 npm 发布同步，将需要正式发布。协调版本和变更日志。
