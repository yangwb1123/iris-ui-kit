# 架构分析：@iris-ui 验证报告驱动的深度审视

## 1. 架构评估

### 1.1 当前优势

| 维度              | 评估 | 证据                                                                    |
| ----------------- | ---- | ----------------------------------------------------------------------- |
| **分层纯度**      | 优秀 | Core 零框架依赖已验证；适配器是真正的薄桥（无业务逻辑泄漏）             |
| **跨框架对齐**    | 卓越 | 149 组件四框架同名同语义；15 个插件包架构一致                           |
| **主题/皮肤架构** | 优秀 | Token 驱动 → CSS 变量 → FOUC 防闪 → 可加载皮肤继承链；设计深思熟虑      |
| **插件系统**      | 良好 | `createPlugin` 契约加法化（非 monkey-patch），`usePluginStore` 类型安全 |
| **质量门广度**    | 良好 | 6 道门（lint + typecheck + test + build + size + format）               |
| **A/B/C 分类**    | 优秀 | 明确的下沉原则防止逻辑泄漏到适配器                                      |

**核心论断成立**：分层架构是业界级设计。Core 的引擎/控制器/纯材料分类，加上 Token 驱动的视觉系统，是 Iris UI 可持续性的根基。AGENTS.md 中的北极星原则（"不要做"清单）表明架构师从第一天就设定了正确的边界。

### 1.2 架构负债与风险

验证报告揭露了四个结构性负债，按严重程度排列：

#### 负债 A：质量保障架构碎片化（严重）

这是单一最大的架构风险。具体表现为：

- **SSR 测试基础设施不统一**：React/Vue 缺少专用的 `vitest.ssr.config.ts`（Solid 和 Svelte 有）。这暗示 SSR 测试策略是逐框架拼接的，而非统一设计的。
- **合同测试覆盖不完整**：13 个缺失的组件全是高复杂度的（Cascader、DatePicker、ColorPicker 等）——构成最高回归风险的组件。
- **基准测试不配套**：单个文件、4 个场景对应 149 个组件。架构中缺乏性能回归检测机制。
- **全无 E2E 测试**：4 个 CMS 应用 + 4 个 SSR 应用 + 3 个桌面壳（desktop-os-{react,vue,solid,svelte,tauri,wails} + desktop）——完全没有集成验证。

**风险本质**：风险是 _复合_ 的。组件级单元测试无法捕获竞态条件、SSR 水合失败、浏览器兼容性、或框架间行为偏差。随着组件库增长，仅靠单元测试的回归防护能力呈亚线性增长——E2E 和合同测试覆盖缺失意味着每次重构都存在未知回归域。

#### 负债 B：Svelte 导出不对称（中等严重）

Svelte 的 `package.json` `exports` 只有 `"."`、`"./form"`、`"./undo"` 和 `"./package.json"`。而 React、Vue、Solid 都使用 `"./*"` 通配符。

实际上，Svelte 的 `src/` 有大约 18 个模块目录（admin、async、behaviors、data、error-boundary、floating、form、i18n、internal、layouts、motion、primitives、provider、resource、skeletons、skins、theme、undo），但只有 2 个通过子路径导出。

**这是架构承诺（"四框架完全对齐"）与实际交付之间的带宽不一致**。Svelte 消费者无法执行 `import { IrisTree } from '@iris-ui/svelte/tree'`，而其他三个框架都支持。这是品牌风险 + 开发者体验摩擦。

#### 负债 C：测试基础设施框架特定偏差（中等）

各框架的测试设置存在细微的不一致性：

- React：5 个顶层测试文件，无专用的 SSR 配置
- Vue：5 个顶层测试文件，无专用的 SSR 配置
- Solid：5 个顶层测试文件 + SSR 配置
- Svelte：4 个顶层测试文件（缺少独立的 SSR 测试）+ SSR 配置

Svelte 缺少独立的 `ssr.test.ts`（相对于其他框架），但通过 `hydration.test.ts`（258 行——实际上最大）来弥补。这种不一致暗示测试是为每个适配器有机增长的，而非由统一的质量框架驱动。

#### 负债 D：基准测试 CI 流程缺失（低严重但值得注意）

`AGENTS.md` 中提到的 "未竟：ROADMAP v3 方向" 包含 "bench CI"。目前基准测试在本地通过 `pnpm bench` 运行，但不包含在质量门中。这意味着性能回归可以在无警告的情况下合入。

### 1.3 关键设计决策：合理性检查

| 决策                                  | 是否合理？ | 备注                                                                                               |
| ------------------------------------- | ---------- | -------------------------------------------------------------------------------------------------- |
| Core 零框架依赖                       | ✅ 正确    | 验证通过；是复用逻辑的基础                                                                         |
| 状态机仅用于有状态的浮层组件          | ✅ 正确    | svjs 退化预防策略很好——防止"布尔 prop + 状态机"的过度复杂化                                        |
| 采用 tsup（而非 rollup/esbuild 裸用） | ✅ 合理    | 多入口配置适用于 React/Vue/Solid                                                                   |
| Svelte 采用 svelte-package            | ⚠️ 需关注  | 这是不对称的根源之一；tsup 的 `"./*"` 通配符无法与 svelte-package 配合，但可通过构建工具流水线解决 |
| 插件不做 `registerComponent`          | ✅ 正确    | 保留了类型推导、tree-shaking 和 manifest 准确性                                                    |
| 皮肤使用 `extends` 继承               | ✅ 正确    | 避免了 NPM 的"密集主题"反模式；部分覆盖 + 组合更优                                                 |

## 2. 扩展方向

### 方向 1：统一质量框架（`@iris-ui/testing`）— P0

**为什么需要**：SSR、合同、基准测试和 E2E 的碎片化质量策略是制约生产就绪的首要障碍。将跨框架测试模式提取到共享包中可以解决 5 个验证缺口中的 4 个。

**核心挑战**：

- 每种测试类型（SSR、合同、基准测试、E2E）的测试工具在框架间存在根本差异。React 需要 `renderToString`，Vue 需要 `@vue/server-renderer`，Svelte 需要 `svelte/server`——抽象层必然会泄露。
- 共享工具包不应引入运行时依赖（保持在 `devDependencies`）。

**预期架构变更**：

```
packages/testing/          # 新增包
  ├── src/
  │   ├── ssr/             # SSR 测试辅助函数 + 类型
  │   ├── contracts/       # 合同测试基类 + 辅助函数
  │   ├── bench/            # 基准测试宏 + 辅助函数
  │   └── e2e/             # Playwright 测试基类 + fixture 工厂
  └── package.json
```

**对现有系统的影响**：

- 各适配器包逐步迁移到 `@iris-ui/testing` 提供的辅助函数。
- 合同测试从内联 harness 转为从共享包继承。
- **向后兼容**：新包是加法——现有内联测试无需重写即可运行。迁移采用 "寄生者优先" 的方式：新组件使用共享包，旧组件按需迁移。

**技术风险**：

- 框架特定 SSR API 的抽象可能会变得笨拙。**缓解方案**：将框架特定的辅助函数放在按框架划分的目录中（`ssr/react.ts`、`ssr/vue.ts` 等），并保留内联逃生口。

---

### 方向 2：Svelte 导出对齐与构建工具统一 — P0

**为什么需要**：修复一个已被验证的架构承诺缺口。若 Svelte 无法与其他三个框架实现同等子路径访问，则 "四框架完全对齐" 的说法不成立。

**核心挑战**：

- svelte-package 无法直接处理 `"./*"` 通配符模式。`dist/` 输出布局必须映射到 `exports` 映射。
- svelte-package 会重新处理组件（Svelte 编译器），因此 tsup 不能直接替代。

**预期架构变更**：
两个方案：

| 方案                                         | 工作内容                                                                     | 优点                                    | 缺点                                                           |
| -------------------------------------------- | ---------------------------------------------------------------------------- | --------------------------------------- | -------------------------------------------------------------- |
| **A：构建后 exports 生成器**                 | 构建后在 `svelte/package.json` 中运行脚本，从 `dist/` 目录扫描推断 `exports` | 无需修改工具链；完全向后兼容            | 额外一步；若无法检测到目录则可能断裂                           |
| **B：将 Svelte 适配器迁移到 tsup + esbuild** | 使用 `svelte/tsup.config.ts` 处理 Svelte 转换（通过 esbuild 插件）           | 工具链一致性；wildcard exports 开箱即用 | 更大幅度的变更；esbuild 的 Svelte 支持不如 svelte-package 成熟 |

**推荐**：方案 A（扫描生成器）作为前一步，方案 B 作为长期目标。方案 A 可以在几天内部署，方案 B 需要验证。

**对现有系统的影响**：

- 所有当前导入 `@iris-ui/svelte`（根目录）的 CMS 应用将继续正常工作。
- 新增的 `@iris-ui/svelte/tree`、`@iris-ui/svelte/floating` 等访问路径不会破坏现有内容。

---

### 方向 3：E2E 测试基础设施 — P1

**为什么需要**：项目有 11 个应用（4 个 CMS + 4 个 SSR + 3 个桌面壳），零集成测试。这是回归检测中最大的黑洞。

**核心挑战**：

- 框架多样性：CMS 应用使用 React、Vue、Solid 和 Svelte。SSR 应用使用 Next、Nuxt、SolidStart 和 SvelteKit。桌面壳使用 Tauri、Wails 和 Electron。
- 单个 Playwright 项目无法覆盖所有——需要针对每种类型的框架特定配置。
- 桌面壳（Tauri/Wails/Electron）不能使用纯 Web E2E 工具；它们需要特定于应用的桥接。

**预期架构变更**：

```
apps/e2e/                  # 新增 monorepo 包
  ├── playwright.config.ts # 针对 CMS + SSR 项目的矩阵配置
  ├── fixtures/
  ├── specs/
  │   ├── cms/             # 跨框架 CMS 规范（四框架使用相同选择器）
  │   ├── ssr/             # SSR 水合规范
  │   └── desktop/         # 仅限 Web 的桌面壳测试（Tauri 需要单独设置）
  └── package.json
```

**对现有系统的影响**：

- 仅新增；不影响现有构建或测试流程。
- Playwright **不应挂钩到 `turbo run test`**（时间太长），而应作为 CI 中的独立门（例如，pr-custom-check）。

**技术决策点**：是只测试 CMS 应用（最丰富）还是包括 SSR 应用？**推荐**：CMS 应用优先——它们覆盖了 149 个组件在真实布局中的使用。SSR 测试已覆盖了渲染路径；E2E 测试应专注于交互和跨框架行为一致性。

---

### 方向 4：合同测试自动化框架 — P1

**为什么需要**：手动维护 13 个缺失组件的合同 harness 代价高昂且容易遗漏。一个声明式（或半自动）合同测试系统可以降低引入新组件的边际成本。

**核心挑战**：

- 合同测试本质上是组件特定的——声明的结构可以共享，但行为断言不能。
- 13 个缺失的组件代表了 Iris UI 中最复杂的组件（DatePicker、Cascader、Transfer、ColorPicker 等）。
- 每个框架需要不同的 harness 实现（React: TSX + testing-library，Vue: 单文件组件 + `@vue/test-utils`，Svelte: `.svelte` 文件 + `@testing-library/svelte`，Solid: TSX + `@solidjs/testing-library`）。

**预期架构变更**：

不是创建新包，而是扩展 `@iris-ui/testing`（方向 1）以包含：

```
packages/testing/src/contracts/
  ├── types.ts             # 合同场景的共享类型
  ├── createContractTest.ts # 场景注册工厂函数
  └── harness/             # 特定框架的 harness 基类（可选）
```

核心洞察：合同测试的*变化点*是 harness（每个组件每个框架 1 个）和场景（每个组件跨框架共享）。通过将场景定义移至 `@iris-ui/core`（作为纯配置对象），harness 变为最小薄包装器。

**对现有系统的影响**：

- 现有 42 个合同场景保持不变；迁移按需进行。
- 新组件合同成为组件导出配置的一部分。

**具体收益**：当添加新组件时，作者提供 1）类型，2）React 实现，3）Vue 实现，4）Solid 实现，5）Svelte 实现，6）合同场景定义。如果场景定义在 core 中，则只需声明一次，四个框架共享。

---

### 方向 5：基准测试 CI 门 — P2

**为什么需要**：目前基准测试存在于仓库中但未投入 CI。在 `turbo run bench` 上设置一个软门（警告而非阻断）可以防止无意的 O(n²) 回归，例如可能出现在 data-view 或 virtualizer 代码中的情况。

**核心挑战**：

- 绝对执行时间因 CI runner 而异。基准测试门必须使用相对比较（该提交与基线的对比）而不是绝对值。
- 基准测试基础设施（vitest bench）支持 `--compare` 标志，但需要基线存储。

**预期架构变更**：

在质量门中添加：

```yaml
# 在 .github/workflows/ci.yml 中
- name: Bench
  run: pnpm bench --compare
  env:
    BENCHMARK_BASELINE: main # 与 main 分支比较
```

**对现有系统的影响**：

- 对架构无影响。纯运维配置变更。
- 基准测试文件需要扩展到覆盖约 9 个缺失的模块（form、pagination、selection、roving 等）。

## 3. 接口设计建议

### 3.1 现有接口设计原则：已验证

当前的 API 设计原则是合理的：

- **声明式 props**：消费者将 Iris UI 组件视为配置文件，而非命令式脚本。
- **除回调外不收函数 prop**：与 AI 原生使用模式一致（LLM 可以生成 JSON props 但不能生成闭包）。
- **每种状态都有 prop**（loading/disabled/invalid/error）：可测试性福利——每个状态都可以通过 prop 直接触发。
- **文案走 i18n**：对国际化友好。

**建议保持**这些原则原样。不建议向 API 表面增加程序化或反射式能力。

### 3.2 新抽象层的必要性

我在当前架构中看到四个时机成熟的抽象缺口：

#### 缺口 A：缺少测试辅助函数包（`@iris-ui/testing`）

如方向 1 中所述。该包的接口应包含：

```ts
// 消费者视角的示意 API（非实现）
import { createSSRTest, createContractTest } from '@iris-ui/testing'

// SSR 测试
createSSRTest('IrisButton', {
  render: () => <IrisButton />,
  assertHydrated: (container) => { /* ... */ }
})

// 合同测试
createContractTest('IrisSelect', {
  scenarios: ['single select', 'disabled option', 'keyboard navigation'],
  framework: 'react', // 或 'vue'、'solid'、'svelte'
  harness: MySelectHarness
})
```

**关键设计决策**：测试辅助函数应该是工厂函数而非基类，以保持组合优于继承。

#### 缺口 B：基准测试注册 API

目前基准测试是手写的 vitest `bench()` 调用。可考虑：

```ts
// packages/core/src/scale.bench.ts  —— 现有模式
bench('construct + initial sync load', () => { ... })
```

对于 9 个缺失模块，一个 `registerBench` 辅助函数可以强制设定命名约定并自动生成 `describe` 套件。但鉴于基准测试文件数量有限，这一点优先级较低。

#### 缺口 C：E2E 测试选择器契约

E2E 测试需要稳定的选择器。当 Iris UI 组件使用 `as-child` 或 `IrisSlot` 时，DOM 输出可能是非确定性的。一个 **data-testid 约定** 应成为 Iris UI 组件接口的正式部分：

```tsx
// 每个 Iris UI 组件渲染时带 data-iris="<ComponentName>"
<IrisButton> → <button data-iris="Button" class="...">
<IrisSelect> → <div data-iris="Select" ...>
```

这为 E2E 测试提供了稳定的选择器，且无需与 CSS 类名耦合。**建议**：将此添加到组件渲染约定中（Layer 1 原语）。这是向后兼容的——现有组件不变，新组件遵守该约定。

### 3.3 向后兼容性策略

| 变更类别                 | 兼容策略                                            | 过渡期     |
| ------------------------ | --------------------------------------------------- | ---------- |
| 新增子路径导出（Svelte） | 新导出是加法；现有 `import` 不受影响                | 无         |
| 新增 `data-iris` 属性    | 可选；消费者 opt in（使用 `as-child` 包裹时不添加） | 永久可选   |
| 合同测试辅助函数         | 新包；现有测试无需重写                              | 无限期共存 |
| E2E 选择性迁移           | 仅新增 E2E 测试文件；无需重写组件                   | 无         |
| 基准测试 CI 门           | `--compare` 标志向后兼容                            | 无         |

**总体原则**：不破坏消费者。Iris UI 是基础设施——破坏性变更是消费者的迁移成本。

## 4. 技术选型

### 4.1 新技术的必要性

| 领域         | 需要变更吗？ | 建议                                                              |
| ------------ | ------------ | ----------------------------------------------------------------- |
| 构建工具链   | 否           | tsup + svelte-package 模式运行良好；仅需修复 Svelte 导出生成器    |
| 测试运行器   | 否           | Vitest 是正确的选择；需要扩展而非替换                             |
| E2E 测试     | **是**       | Playwright 是自然选择（与 Vitest 生态兼容，跨浏览器，支持移动端） |
| 性能基准测试 | 否           | Vitest bench 已足够；需要在 CI 中启用                             |
| Lint/格式    | 否           | ESLint 9 flat + Prettier 3 是最佳实践                             |
| 文档         | 否           | VitePress 是最佳选择                                              |
| 桌面测试     | 视情况而定   | 若 E2E 扩展到桌面壳，针对 Tauri/Wails/Electron 的 Playwright      |

### 4.2 Playwright vs Cypress vs TestCafe

若新增 E2E 测试，Playwright 是明显赢家：

| 标准       | Playwright                              | Cypress                       | TestCafe           |
| ---------- | --------------------------------------- | ----------------------------- | ------------------ |
| 框架支持   | 原生跨浏览器（Chromium/Firefox/WebKit） | 仅 Chromium（跨浏览器实验性） | 跨浏览器           |
| 测试隔离   | 原生浏览器上下文                        | `cy.visit()` + 清理           | 隔离但性能开销更高 |
| 并行性     | 原生分片                                | 需要 Dashboard 服务           | 原生分片           |
| 工具链兼容 | Vitest + Playwright 协同良好            | Cypress 是独立的              | 独立               |
| 桌面应用   | 通过 Electron 集成                      | 有限                          | 有限               |
| 社区采用   | 行业新标准                              | 成熟但正在衰退                | 小众               |

**建议**：Playwright。与现有 Turborepo + Vitest 工作流程集成。可以通过 `@playwright/test` 安装为 devDependency，无需新服务。

### 4.3 自建 vs 采购清单

| 组件              | 决策                                          | 原因                                     |
| ----------------- | --------------------------------------------- | ---------------------------------------- |
| E2E 测试基础设施  | **采购**（Playwright）                        | 行业标准；无需构建                       |
| 合同测试框架      | **自建**（`@iris-ui/testing`）                | 领域特定；无现成替代品                   |
| 基准测试 CI 门    | **配置**（Vitest bench 原生支持 `--compare`） | 现有工具中已有                           |
| 性能预算门        | **配置**（`pnpm size` 已存在；扩展即可）      | 已用 `size-limit` 实现                   |
| SSR 测试辅助函数  | **自建**                                      | 框架特定 SSR API 需要 Iris UI 感知的封装 |
| Svelte 导出生成器 | **自建**（~50 行脚本）                        | 简单扫描 + 生成；不值得独立依赖          |

### 5.3 风险与缓解

| 风险                                            | 可能性 | 影响 | 缓解                                                                                                          |
| ----------------------------------------------- | ------ | ---- | ------------------------------------------------------------------------------------------------------------- |
| **R1** Playwright 配置困难（框架多样）          | 中     | 高   | 先锁定 cms-react；每个新框架逐步添加独立的配置文件                                                            |
| **R2** svelte-package 无法支持 wildcard exports | 高     | 中   | 方案 A（后构建脚本）可 100% 规避此风险；方案 B（tsup 迁移）是长期冗余方案                                     |

| **R4** 基准测试 CI runner 稳定性不佳            | 中     | 低   | 使用相对回归（`--compare main`），阈值设为 20%，不用绝对值；标记失败为警告而非阻断                            |

## 6. 总结与建议

### 关键洞察

**Iris UI 的架构基础是扎实的**。分层隔离、A/B/C 逻辑分类、Token 主题系统和跨框架对齐都是业界级的设计。验证报告确认了 5 个缺口，但没有一个是根本性的架构缺陷。

最大的风险是**质量架构碎片化**——并非组件设计不当，而是缺少完备的回归检测网。好消息是：这些缺口是*可操作的*且*边界清晰*。每个都有明确的修复路径，不破坏现有代码。

### 最重要的三个建议

1. **Svelte 导出对齐（P0，第 1 周）**：最便宜的修复，影响最大的架构承诺可信度。一个简单的后构建脚本就可以解决。不做不行。

2. **E2E 测试（P0，第 2-3 周）**：Playwright + cms-react 是回归检测中价值/成本比最高的。从 5-10 个场景开始，确认测试基础设施正确后再扩展。

3. **`@iris-ui/testing` 包（P1，第 4-5 周）**：这是长期质量可持续性的倍增器。一旦到位，新增组件时包含 SSR + 合同测试的成本会大幅下降。

### 不建议的事项

- ❌ **不要用 Storybook 替换合同测试**——Storybook 是浏览工具，不是测试框架。合同测试验证行为是否正确，Storybook 验证组件是否可浏览。
- ❌ **不要在 npm 发布前启动所有 15 周 plan**——阶段 1 足以安全发布。阶段 2-4 是增量改进。
- ❌ **不要统一 SSR 测试基础设施到极致**——框架的 SSR API 不同；一个"最低公共分母"的封装层会变得抽象。按框架划分的辅助函数 + 共享类型就足够了。

---

这份分析确认验证报告的发现是真实的，并将它们映射到可操作的架构决策中。三个 P0 项可在一月内完成，并消除 5 个已识别缺口中的 3 个。剩余两个（基准测试 + 完整合同覆盖）是增量改进，可以安全地让步于 npm 发布。
